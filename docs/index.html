HTTP server

Your Ruby app, as one binary.

You write a class for each resource. The decision graph answers the rest of HTTP. HTTP/1.1, HTTP/2, WebSocket, server-sent events, static files and TLS are on board, and at run time it needs OpenSSL 3 and nothing else.

$ rake $ mrbc -g -o app.mrb app.rb $ webmachine-server --app=app.mrb
Run it in five minutes Read the source

app.rb

# A resource answers for one thing. Name the
# media types, and write the body.
class Article < Webmachine::Resource
  def self.content_types_provided
    [['text/html',        :to_html],
     ['application/json', :to_json]]
  end

  def to_html
    "<h1>#{request.path}</h1>"
  end

  def to_json
    %Q({"path":"#{request.path}"})
  end
end

def main
  Webmachine::Application.new do |app|
    app.conf.port = 8080
    app.add_route ['articles', :id], Article
  end
end

Proof, with the method beside it

Measured, not claimed

Optimised from the accept to the last byte written, and across the board rather than on one favoured path: heads are prebuilt, a folded answer is kept as bytes, sends avoid a copy where the kernel allows one, and the size of the hot functions is measured so the rare paths stay out of them.

It runs on io_uring where the kernel allows it. slipstreamIO carries the same rings to Linux without io_uring, to macOS, the BSDs and Windows.

Both figures are one core, over a unix socket. Every run is in bench/results/ with the command that produced it, and bench/how-to-measure.md explains how to get a number you can trust on your own hardware. The same asset sweep runs against nginx with gzip_static, against lighttpd and against h2o, with the same columns, so the rows sit next to each other and mean the same thing. A number from someone else's machine is a starting point, not a result.

How it works, 1 of 2

The half of HTTP you did not write

Every request walks the same graph. Each node asks one question and cites the clause it comes from. You override the handful your resource cares about, and the rest answer themselves, so correctness is not a thing you have to remember to write.

The callback names are webmachine-ruby's, so its documentation applies here.

How it works, 2 of 2

When an answer never changes, move it to the class

A callback written def runs per request, which is how most of them are written. Write one def self. and the server calls it once at start instead, then keeps what it answered as bytes: the status line, the head, the ETag and the HTTP/2 header block.

A request against a resource folded that way is a lookup and a write. The server tells you at start if a callback is written the wrong way for what it does.

Nothing says the answer has to be a constant. A folded callback can read files, walk a directory and render templates while the server is coming up, which is a site generator that runs at start and leaves its output in memory rather than on disk.

Doing the work at start and holding it in memory is a choice you make, never a condition of using the server. You can make an answer as static or as dynamic as HTTP itself allows, one callback at a time. 

# Per request, the ordinary form.
def to_html
  "<h1>#{request.path}</h1>"
end

# Once at start, kept as bytes.
def self.to_html
  '<h1>About</h1>'
end

Send a block to a worker thread with a deadline. Each worker has its own VM and its own ring. The flow waits, the loop that takes requests does not.

Work that must not block

Two declarations, and the loop keeps taking requests

A callback that waits says so on the class. The flow stops at that node and goes on with the answer. Nothing else on the server waits with it.

compute: a worker thread answers

The block leaves the request loop. Each worker has its own VM and its own ring. A dumped block carries no environment, so you pass what it needs as an argument, or you build it once per worker in the registry. 

Webmachine::Workers::Registry[:passwords] = proc do
  { 'ada' => Argon2.hash('secret')[:encoded] }
end

class Login < Webmachine::Resource
  compute :is_authorized?

  def is_authorized?(header)
    Webmachine::ComputeTask.new(header,
                                max_runtime: 200.ms) do |h|
      user, pass = h.to_s.split(':', 2)
      db = Webmachine::Workers::Registry[:passwords]
      stored = db[user]
      stored ? Argon2.verify(stored, pass.to_s) : false
    end
  end
end

A task over its deadline answers 500. A worker that raises answers 503 with a Retry-After field.

watch: a descriptor answers

The block stays in the request loop, so it keeps request and response in reach. It runs each time the descriptor is ready, until it says abort, and its last value is the answer. 

DB_IDLE = []   # one thread, so an Array is a pool

class Article < Webmachine::Resource
  watch :generate_etag

  def generate_etag
    conn = DB_IDLE.pop ||
           Pq.new(DB_URL).tap { |c| c.nonblocking = true }
    conn.send_query('select etag from articles')
    Webmachine::Watcher.new(conn.socket, :r,
                            timeout: 2.s) do |ready, w|
      next w.abort if ready == :timeout
      conn.consume_input
      next if conn.busy?      # not whole yet
      w.abort
      etag = conn.get_result.to_ary[0][0]
      conn.get_result         # the nil that ends the set
      DB_IDLE << conn
      etag
    end
  end
end

Every other connection is served while this one waits for the database.

What it replaces

Things you would otherwise install a tool for

The server runs with no application at all when all you need is files, so a few of the specialised tools around a site stop being separate pieces.

--standalone --docroot=DIR

A file server

What you would reach for python3 -m http.server or npx serve to do, with ETag, gzip, HTTP/2 and TLS on it.

$ webmachine-server --standalone --docroot=./public --port=8080
def self.

A site generator you never run

Your Ruby builds the pages when the server comes up, reading whatever you keep them in. Each one is kept as bytes and answered from memory after that. No generator, no output directory, no build step to forget. This is one option and not a rule. The same resource written to run per request works, and you pick per callback.

$ mrbc -g -o site.mrb site.rb $ webmachine-server --app=site.mrb
rake pack[DIR,OUT.zip]

Files you already have

A directory of assets, or a site something else built, zipped once. The pack is mapped and every file answers from memory, with its ETag and its compressed form ready.

$ rake pack[public,site.zip] $ webmachine-server --standalone --assets=site.zip

Before you try it

The questions an engineer asks first

Is mruby a real Ruby?
It is the Ruby of ISO/IEC 30170, made to embed. A resource is plain Ruby: classes, blocks, strings, hashes. Libraries are mrbgems, compiled into the binary, not gems installed at run time. Rails does not run on it, and this server is not a framework.
One thread. What happens when a callback waits?
It says so on the class. compute sends the block to a worker thread with a deadline. watch waits on a descriptor without leaving the loop. Every other connection is served while it waits.
Where does TLS come from?
The TLS 1.3 handshake is OpenSSL 3. Then the keys go to the kernel, and a plain send is a TLS record. Linux and FreeBSD have that. On a kernel without kTLS a listener that serves TLS refuses to start and names the reason. Then you run plain HTTP, and a proxy in front does TLS.
Which platforms?
io_uring where the kernel allows it. slipstreamIO carries the same rings to Linux without io_uring, to macOS, the BSDs and Windows. Without io_uring every socket operation is readiness plus a classic call: correct, and slower.
What does a build need?
A C++20 compiler, ruby for the build system, git, pkg-config, zlib and OpenSSL headers. At run time: libz, libssl 3 and libstdc++. The build stops and names the missing package.

Get started

Three commands, then the tutorial

A clone and one rake build everything. Compile your app to bytecode and start the server. The tutorial takes it from there, one step at a time, to a resource that answers a conditional request with 304.

$ git clone --recursive https://github.com/Asmod4n/webmachine-mruby $ cd webmachine-mruby && rake $ mruby/bin/mrbc -g -o hello.mrb hello.rb $ mruby/bin/webmachine-server --app=hello.mrb

rake install[PREFIX] puts the four programs under PREFIX/bin. docs/container.md builds and runs it in a container. The build makes four programs:

webmachine-serverruns your app. One thread takes the requests, and compute workers take the work that must not stop it
mrbccompiles your Ruby to bytecode, the form the server runs
webmachine-logdwrites the access log and the error log
webmachine-passwdkeeps the password database, argon2id in LMDB
