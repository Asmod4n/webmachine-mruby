# .DESIGN.md

Why this tree is shaped the way it is.

The source carries one line above each function: **which RFC it serves**.
Everything else — why a clause is executed that way, what was measured,
what was tried and buried, what a kernel actually does as opposed to
what its manual page says — lives here, filed under the RFC the code's
header names. A function whose header names no RFC serves one of the
domains under *Beyond the RFCs*, and that is where its reasoning sits.

That split is the whole convention: **the header is the index entry,
this file is the article.** Read the function, read its RFC line, come
here for the paragraph.

<a id="following"></a>
## Following a link from the source

Every function header ends with the path to this file, the anchor of
the section that holds its reasoning, and that section's heading:

```cpp
// RFC 9113 6.2/6.9.1: HEADERS and DATA for one stream; DATA beyond
// min(connection, stream) is PARKED, never written.
// .DESIGN.md #h2-cache "The per-connection response cache"
bool Http1::h2_answer(...)
```

Three tokens, because no single one works everywhere:

| token | what it is for |
|---|---|
| `.DESIGN.md` | a plain repo-relative path - the one form every editor's path handling understands |
| `#h2-cache` | a unique token: project-wide search lands on the heading and on every call site that points at it |
| `"The per-connection response cache"` | the heading itself, so the part can be found by reading rather than by tooling |

**The path and the anchor are separated by a space, deliberately, and it
was measured rather than assumed.** vim's default `isfname` contains `#`
(`:set isfname?` gives `@,48-57,/,.,-,_,+,,,#,$,%,~,=`), so `gf` on a
glued `.DESIGN.md#h2-cache` looks for a file of that literal name and
fails. Split, it opens this file:

| in the comment | vim `gf` on the path |
|---|---|
| `.DESIGN.md#h2-cache` | fails - `#` is part of the filename |
| `.DESIGN.md #h2-cache` | opens `.DESIGN.md` |

What that means per editor:

- **vim / neovim**: `gf` on the path (measured above); `*` on the anchor
  then jumps to the heading.
- **Emacs**: `M-x ffap` on the path.
- **JetBrains**: relative paths in comments resolve, so the path is
  ctrl-clickable.
- **VS Code / VSCodium**: the path is **not** clickable, and no spelling
  of it would be. Editor link detection only linkifies URIs with a
  scheme, and the only schemes that could work here (`file:`, `vscode:`)
  need an absolute path, which has no business in a repo. The integrated
  terminal does resolve relative paths, but that is a different link
  detector from the editor's. What works there without configuring
  anything: `Ctrl+P` and type `DESIGN` for the file, `Ctrl+Shift+F` on
  the anchor for the section.
- **Anything else** - `rg`, `git grep`, GitHub's search: the anchor is
  the universal handle.
- **GitHub and any Markdown viewer**: the anchors are real HTML ids, so
  pasting `.DESIGN.md#h2-cache` as a URL fragment resolves.

The ids are written by hand rather than derived from the heading text,
so rewording a heading never breaks a link - and the heading travels in
the comment beside the id, so a reworded heading shows up as a mismatch
instead of rotting silently. They are prefixed by domain: `h-` for HTTP
semantics, `h1-`, `h2-`, `hpack-`, `ws-`, `pmd-` (permessage-deflate),
`sse-`, `gz-`, `zip-`, `flow-`, `ring-`, `deliver-`, `mruby-`, `app-`,
`log-`, `cfg-`.

<a id="commandments"></a>
## The commandments

The founding commit's rules, unchanged, because most of what follows is
one of them applied to a concrete line:

1. Only code the HTTP state model demands.
2. Comments carry a number, a contract or a clause, or they do not exist.
3. A VM entry is budgeted, not taken.
4. Bounds checks are `if`s before the write, never asserts.
5. The warm path allocates nothing, and our buffers never come from the
   VM's allocator.
6. No locking, ever.
7. One framer, one writer, one flow.
8. Tests assert bytes on real sockets.
9. The harness line is part of every number.
10. Defaults never flip on one environment's evidence.
11. One implementation, one path — no silent fallback.
12. Foreign code only for fleet-proven security-critical codecs.
13. Bounded work per tick (numbered 18 in the source's own references).

And the addendum: *only what is needed, and always the fastest existing
variant of it.*

<a id="rfc9110"></a>
# RFC 9110 — HTTP Semantics

<a id="flow-graph"></a>
## The decision graph

The specification is webmachine-ruby's `lib/webmachine/decision/flow.rb`.
This tree carries that graph **as data**: every node keeps that file's
name, its callback and both edges, and every decision names the RFC
clause it executes. There is no interpreter — the table *is* the state
model, and a compile-time walk proves it terminates.

Each node declares where its decision comes from, because that is what
the tiers are built from:

| kind | decided by | cost |
|---|---|---|
| `kRequest` | the parsed request — method, header presence, machine state already at hand | never enters the VM |
| `kResource` | a resource callback | konst per class folds it into the graph; otherwise one budgeted VM entry (measured 95–191 ns, cached symbol) |
| `kConneg` | a resource-provided list negotiated against a request header | konst when the list is constant |
| `kAction` | performs the request's work (delete, create, body) | — |

Four properties are proven when the header compiles, so the walker and
the table cannot drift from flow.rb's semantics without failing the
build: the table is indexed by its own ids (position and id agree),
every edge points at a real node or halts with a real status, every
path from B13 reaches a halt within the node count (a cycle would
overrun the depth bound), and every node is reachable from B13 (a dead
entry would be an untested lie).

<a id="flow-shortcut"></a>
## Run only what cannot be predicted

A konst vector decides most of the graph at `add_route`, and the method
is folded into it. Measured on the default resource:

| method | nodes visited | of them request-dependent |
|---|---|---|
| GET / HEAD | 46 | 21 |
| POST / PUT / DELETE / OPTIONS | 4 | **0** |
| OTHER | 2 | **0** |

Four node visits per request to rediscover a fixed 405. Two values
computed once per resource × method retire both cases:

- `status` — the answer when nothing is left to decide. It comes from
  the **same** walk the request path uses, run once with every header
  fact false. No second interpreter to drift from the first.
- `always` — does any reachable node read the request at all? The
  reachability probe explores **both** branches at a `kRequest` node
  (either may be taken at runtime) and follows the konst answer
  everywhere else.

`flow::answer` is then two integer tests standing in for the graph
whenever the graph could not have said anything else; everything
conditional still walks it, so the answers cannot differ.
`test/flow.rb` proves that exhaustively — for every method and every
combination of header facts, `answer(...) == walk(...)`.

`ReqFacts::plain` is what makes the shortcut legal: true while every
header-derived fact is still false, cleared in `http::header_switch`,
the one place those facts are born and the one both framers share.

<a id="flow-bitset"></a>
### A bitset walk was measured and removed

All answers in one word, branchless request bits, no switch. It **lost**
to the plain interpreted walk on both machines — forgecore 37.2 vs
34.0 ns, Pi 87.7 vs 81.9 ns: the branchless bit build cost more than
the predicted switch saved. History holds the code, the numbers hold
the verdict.

One open question is attached to that grave: on a noisy shared vCPU it
**led** (container 60 vs 70 ns). If a cloud instance ever becomes a
measured target, resurrect and re-measure **there** — never on this
evidence alone. Note the path branches (one edge per node) are
identical in both; only the dispatch differed.

<a id="h-target"></a>
## §4.2.1 — the query is not part of the path

Cut off once, before any route is compared. The router, the asset tier
and the request object all read the same boundary through the same
`http::path_only`.

<a id="h-field-names"></a>
## §5.1 — field names are case-insensitive

Which is why `request.headers` **lowercases**: h2 puts names on the wire
lowercase (RFC 9113 §8.2) and h1 says they are case-insensitive, so
lowercasing is what makes one name mean one thing whichever wire
carried it. A repeated field is joined with `", "` — the same value
list the sender could have sent (§5.3).

<a id="h-field-limits"></a>
## §5.4 — oversized fields may be refused

8 KiB is the fleet convention (nginx, h2o) and bounds one head's work;
past it, 431. Bodies are skipped at this layer, but skipping is still
work: 1 MiB bounds it, and past it 413 (§15.5.14).

<a id="h-date"></a>
## §5.6.7 — the Date field

IMF-fixdate is spelled **by hand**. `strftime`'s `%a`/`%b` obey the
process locale and would emit German day names under `LC_TIME=de_DE`.

Writers prebuild responses with a placeholder and patch exactly those
29 bytes once a second. h1 patches its prebuilt strings in place; h2
sends the date through the HPACK encoder lane instead, where the
connection's dynamic table turns it into a one-byte reference for both
sides until the second rolls.

<a id="h-connection-list"></a>
## §7.6.1 / §7.8 — Connection is a token list

A substring match would accept `not-close`. And because it is a *list*,
a browser's `Connection: keep-alive, Upgrade` needs a third test on the
same list, not an `else`. §7.8 also lets a server ignore an upgrade it
does not offer — which is exactly what happens when a path names no
websocket route.

<a id="h-content-type"></a>
## §8.3 — a body announces its Content-Type

`MimeDb::type_of` never returns null: a generic claim
(`application/octet-stream`) is only worse than no claim when it lies,
and octet-stream never does.

<a id="h-charset"></a>
### charset, and why only text/*

`text/*` with no parameters gets `; charset=utf-8` appended — a
statement of fact, not a guess: mruby produces UTF-8 or bytes, nothing
else exists in this VM, and a `text/plain` response without a charset
decodes by the **browser's** locale default (windows-1252 in Western
locales). `application/json` is left alone: its registration has no
charset parameter (RFC 8259, JSON is UTF-8) and adding one is noise. A
type already carrying parameters is left alone — a resource that
spelled its own charset wins.

Setup-only, never per request, and **every** writer goes through the
one function: Http1's konst heads, the h2 blocks, and the asset tier's
extension table. This tree once shipped two serializers that drifted
apart, which is the whole reason there is one now.

<a id="h-content-length"></a>
## §8.6 — Content-Length

Spelled by hand; printf machinery has no business on the request path.
Parsed as `1*DIGIT` with overflow builtins: a syntax violation is the
caller's 400, an overflow past `size_t` is the caller's 413.

<a id="h-etag"></a>
## §8.8.3.3 — ETag

The asset tier's ETag is the Central Directory's CRC-32, quoted. It
names the **uncompressed** data, and because exactly one representation
is ever served per entry, no collision across coding boundaries is
possible — no suffix needed.

<a id="h-head"></a>
## §9.3.2 — HEAD

HEAD renders too, because its Content-Length must be the GET's, and
then sends no body bytes.

<a id="h-allow"></a>
## §10.2.1 — Allow

405 names what **is** allowed, from *this* resource's list. That is the
whole reason a 405 needs a per-route entry rather than the shared
status store.

<a id="h-conneg"></a>
## §12.5 — content negotiation

C3/D4/E5/F6 decide on header **presence** (a request fact); the
resource's list only feeds the default negotiation. The default
resource's provided lists negotiate every request; value-dependent
conneg — a narrow Accept against a narrow list — is a later tier and
not a konst bit.

<a id="h-accept-encoding"></a>
### §12.5.3 — Accept-Encoding, asked one question

May gzip be sent? Most specific wins: an explicit `gzip` (or its
`x-gzip` alias) decides by its own q; otherwise `*` decides; otherwise
the field is present and names neither, so gzip is not acceptable. An
empty value means "no codings" and is also not acceptable. Callers only
ask when the field **exists** — a missing field means any coding is
acceptable and never reaches the parse. Weight is `0[.000]..1[.000]`,
so "any nonzero digit" *is* "q > 0".

`identity` needs no `encodings_provided` key at all: §12.5.3 makes it
always available, and for a dynamic body this tree can always produce
it, so F6/F7 never need to refuse.

<a id="h-vary"></a>
### §12.5.5 — Vary

A resource that *can* gzip carries `Vary: Accept-Encoding` on the
identity answer too — it varies by coding whichever branch was taken.
And a cache must not be handed the gzip answer for a client this tier
would refuse with 406, which is why the asset tier's 200 carries Vary
as well.

<a id="h-etag-lists"></a>
## §13.1.1 / §13.1.2 — If-Match and If-None-Match

`*` is carried as a fact and never reaches the list parse; a quoted
`"*"` arrives from some clients and means the same. If-None-Match
compares **weakly** — a `W/` prefix is stripped and ignored;
If-Match compares **strongly**, so a weak member can never match there.
An element that is not an entity-tag is skipped to the next element
rather than trusting the rest of a malformed list.

<a id="h-range"></a>
## §14 — Range

Never touches the graph: webmachine has no range node, because a range
is a representation concern and not a decision one. It sets no fact and
leaves `plain` alone; only the asset tier reads it.

- **§14.1.2** — `bytes=first-last | first- | -suffix`, **one** range
  only. `complete` counts the **selected representation's** octets: for
  a `Content-Encoding: gzip` response that is the compressed stream.
  Ranging the uncompressed bytes under a gzip coding would be silent
  corruption.
- **§14.2** — a server MAY ignore Range entirely, so a multi-range
  request, a foreign unit or a malformed value degrades to the full
  200. Stated here rather than discovered. Range is defined for GET
  alone; a HEAD carrying Range answers the plain 200 head.
- **§14.2** — If-Range holds **one** validator, compared strongly (a
  weak tag can never match) or an HTTP-date. The date form is unparsed
  here, and an unmatched validator lawfully serves the full 200, so a
  date reads as "no match" and stays correct.
- **§14.3** — `Accept-Ranges` is advertised because it is true: both
  ZIP methods range over the wire body through the same `copy_wire`.
- **§14.4 / §15.3.7** — the satisfied range and the complete length,
  both counting wire-body octets. **§15.5.17** — the unsatisfied form
  names the complete length.

<a id="h-status"></a>
## §15 — status codes

The status **names** come from §15. 204 and 304 are defined bodyless
(§15.3.5 / §15.4.5): no Content-Length, no body. A 304 repeats what a
cache updates by (§15.4.5): ETag, and Vary where the 200 carried it.

<a id="h-406"></a>
### The asset tier's 406 deviates from a SHOULD, by name

§12.5.3 says a server should fall back to no coding — *assuming it can
produce an uncompressed representation*. This tree deliberately cannot:
there is no inflate anywhere. §15.5.7 sanctions the refusal, and this
is where that is written down.

<a id="h-token"></a>
## §5.6.2 — token

Which is what RFC 7692 §4.2's extension-param names and unquoted values
are, so the token parser is shared.

<a id="rfc9112"></a>
# RFC 9112 — HTTP/1.1

One framer (picohttpparser on the wire bytes, a carry only when a head
splits across receives), one writer (prebuilt response strings for
every status the flow can speak, the running second patching 29 date
bytes in place — a response is a single append), one flow. The framer
only ever decides **wire validity**; the graph decides every status.

<a id="h1-bad-request-line"></a>
## §2.2 — a request line that does not parse

400 with `Connection: close`.

<a id="h1-smuggling"></a>
## §6.1 / §6.3.3 — request smuggling

A second `Content-Length` is a smuggling shape and is refused.
`Transfer-Encoding` alongside `Content-Length` is the classic vector;
chunked alone is refused with 411, as §6.1 sanctions, until a body
consumer exists.

<a id="h1-chunked"></a>
## §7.1 — chunked

Each SSE event is one chunk and the stream ends with the terminal
chunk. It is the only framing that lets a message stay legal without
knowing its own length.

<a id="h1-connection"></a>
## §9.3 — Connection semantics

1.1 persists unless it says close; 1.0 closes unless it asked (§C.2.2,
the echo rule), and the asked-for keep-alive is echoed back. So the
three prebuilt spellings are: a persistent 1.1 response carries **no**
Connection header, a persistent 1.0 echoes keep-alive, anything closing
spells close.

`kKeep` is 1.0-only *and* only on request. Those three literals live at
exactly one place, indexed by the enum that names them — they used to
stand twice in `assets.cpp` (prebuilt heads, and a switch for
per-request heads), which is how two spellings of one table drift
apart. This tree paid for that lesson once already.

<a id="h1-close"></a>
## §9.6 — a close ends the exchange

Bytes pipelined behind a closing request die with the connection. And
the other direction: `next` drains **before** a pending close, because
an error response queued behind an in-flight send must still reach the
wire.

<a id="h1-framer"></a>
## The framer's own shapes

- The head cap holds for **complete** heads too, or one receive
  carrying a whole oversized head would sail past the split-head check.
- Body bytes a previous receive left owing are consumed first —
  skipped, since this layer has no consumer, but the framing must hold
  or keep-alive would parse body bytes as the next head.
- An active transfer owns the wire order: responses to anything
  pipelined behind it would overtake its remaining chunks, so those
  bytes wait in the carry and `more()` resumes parsing them when the
  source is exhausted. One head's budget bounds the wait — a peer
  stuffing more than that behind a running transfer wants buffer, not
  service, and RFC 6585 §5 sanctions the refusal. Mid-body no status
  can be spoken at all (the bytes would land inside the transfer's
  Content-Length), so the connection just ends.

<a id="rfc9113"></a>
# RFC 9113 — HTTP/2

The same konst vectors, the same run frame, the same sink. A connection
that spoke the preface routes its bytes to the frame layer instead of
through phr, and only the serialization differs.

**Deliberately absent:** priority trees (deprecated by 9113) and server
push (§8.4 forbids the client side; nothing here wants the server
side). Request bodies are counted and discarded — exactly the tier the
h1 framer is at.

<a id="h2-preface"></a>
## §3.4 — the connection preface, and the one h2spec case this tree fails

The preface splits into an **announcement half** — the 18 bytes
`PRI * HTTP/2.0\r\n\r\n`, which no HTTP/1 request line can be a prefix
of — and the rest. **Where** the mismatch falls decides who the peer
is, and that is the whole of §3.4's advice: *"an invalid preface
indicates that the peer is not using HTTP/2."*

- **Past** the announcement: the peer has named itself an h2 client and
  then fumbled. It is waiting for a frame and cannot read a status
  line, so it gets the frame §3.4 names — GOAWAY, PROTOCOL_ERROR,
  last-stream-id 0 — and the connection ends.
- **Before** it: the peer never said `PRI`, so by §3.4's own sentence it
  is not an h2 client. This listener also speaks HTTP/1.1, so it gets
  the HTTP/1.1 answer to a request line that does not parse: 400,
  `Connection: close`.

That second branch is the one h2spec case this tree does not pass
(3.5/2, *"Sends invalid connection preface"* — h2spec sends
`INVALID CONNECTION PREFACE\r\n\r\n` and reads our status line as a
frame header). **Named, not accidental:** h2spec measures an h2-only
endpoint, the connection dies either way as §3.4 requires, and the
alternative — closing a fresh connection mute — would take the 400 away
from every real HTTP/1 client that mistypes its first request line.

The detection itself costs one compare per connection, never per
request: GET diverges at byte 0, POST/PUT at byte 1.

The server's own half of the preface is a SETTINGS frame with one
entry, the concurrency cap. Everything else keeps its default, and
saying so would only be bytes.

<a id="h2-frame-size"></a>
## §4.2 — frame size

Ours, and also the floor every peer must accept. A peer's smaller cap
is stored clamped: frames smaller than the peer's cap are always legal,
and our buffers are sized to the floor.

<a id="h2-streams"></a>
## §5.1 — the stream state machine, out of two numbers

A stream **in the table** is open (or half-closed); an id **above**
everything ever accepted is idle; anything else is closed. Idle and
closed earn different errors on almost every frame type, which is the
whole reason the highest-accepted id is kept instead of the dead
streams. That is what makes the distinction free.

- DATA on an idle stream is a **connection** error; on a closed one it
  is the stream's, and the connection lives.
- HEADERS opens a stream, and only an idle id can be opened — an id at
  or below the highest ever accepted is either closed or out of order,
  and both are the connection's error (§5.1.1).
- A stream answered in full inside its own dispatch **never enters the
  table**. Opening it only to close it at the end of `h2_answer` cost
  an `emplace_back` with a `std::string` member, two more linear scans
  and the matching destructor — per request, on the hot path. The facts
  live on the dispatch's stack, which is all the answer needs.
- §5.1.2 counts **open** streams, so the concurrency cap counts streams
  the connection still owes something: a body to arrive, or a parked
  remainder to drain. A peer past the cap is refused per stream, not
  per connection.
- §5.3.1: a stream may not depend on itself. PRIORITY is deprecated, so
  the five bytes are skipped — but that check is a check, not a
  priority tree, and §6.3 still gives PRIORITY a stream of its own
  (never 0).

<a id="h2-frames"></a>
## §6 — frames

- **§6.4 RST_STREAM**: stream 0 and an idle stream are the connection's
  error; a wrong length is its own.
- **§6.5.2 SETTINGS**: ENABLE_PUSH is 0 or 1 and nothing else. This
  server never pushes either way (§8.4), so the *value* changes nothing
  here — the refusal is about the peer being wrong. A new
  INITIAL_WINDOW_SIZE reflows onto every live stream (§6.9.2).
- **§6.9 flow control**: debits follow DATA. Nothing is debited where
  nothing is sent. DATA beyond `min(connection, stream)` is **parked,
  never written** — writing it anyway is the violation that earns a
  GOAWAY (§6.9.1). A window past 2^31−1 is the **stream's** error, not
  the connection's: the stream dies, the peer keeps talking. An idle
  stream has no window to update (§5.1).
- **§6.10 CONTINUATION**: a header block owns the connection until
  END_HEADERS; nothing else may interleave.
- **§8.4**: a client must not push.

<a id="h2-trailers"></a>
## §8.1 — trailers

Legal only as the very end of the request. Their fields are decoded —
the dynamic table demands it — and not forwarded.

<a id="h2-malformed"></a>
## §8.1.1 — malformed is a stream error

Not a connection error; the frame loop carries on. And DATA framing
already delimits, so a status at this tier spells no Content-Length.

<a id="h2-content-length"></a>
## §8.1.2.6 — content-length is a claim

What the request *claims* its body is, compared against the DATA that
actually arrives. The disagreement can only be seen at END_STREAM,
which is why the claim is remembered on the stream. END_STREAM on the
HEADERS means no DATA is coming, so a non-zero content-length was a
claim about a body that never existed.

<a id="h2-pseudo-fields"></a>
## §8.2 / §8.2.2 / §8.3 — the pseudo-fields

Pseudo-fields first; exactly **one** `:method` / `:scheme` / `:path` —
a second one is not a later value winning, it is a malformed request.
Field names are lowercase. Connection-specific fields make the request
malformed; `te` may say `trailers` and nothing else.

<a id="h2-lanes"></a>
## Sending: two lanes

**Lane 1, precomputed** — only what never changes: `:status`,
konst `content-type`, `allow`. Encoded never-indexed, so the bytes are
connection-independent, which is exactly what makes precomputing them
legal. Costs a 9-byte frame header plus one memcpy per response.

**Lane 2, the encoder** — whatever changes per request goes through
ls-hpack and the connection's dynamic table. Today that is the date;
the value tiers (etag, location, …) join it when they land.

Never-indexed literals touch no table state on either side, so the two
lanes interleave freely in one header block.

<a id="h2-cache"></a>
### The per-connection response cache

**One slot, deliberately not one per status.** Homogeneous traffic (the
common case) gets the full win; a status change falls back to
rebuilding it fresh — the same cost as before the cache existed, never
wrong. The route joins the key, because the same status means different
bytes for different resources (content-type, allow).

`bytes` holds a whole HEADERS frame and, when the body qualifies, the
whole DATA frame right behind it — so the common answer is **one
append** of one contiguous buffer, the way h1 answers. Everything in it
is fixed except two 4-byte stream ids and one flags byte, at the
offsets `h2_put_frame_header` defines.

The DATA frame joins the cache only when the body is konst (`!bound` —
then it is the same bytes for the life of the process) **and** small.
The cap is the whole argument for the size: this saves per-call
overhead, and past a kilobyte the memmove dominates that anyway, while
the copy is per **connection**. Small bodies get one append; large ones
keep the two they already had and lose nothing.

<a id="h2-decode-buffer"></a>
### The decode buffer's high-water mark

`resize()` **value-initializes**. Growing the header buffer per field
zeroed 4 KiB of scratch that ls-hpack overwrites immediately: 16 KiB
per 4-field request, measured on forgecore as the single largest
h2-over-h1 cost — **+2.42 % in memset, more than `h2_answer` itself**.
Keeping a cursor and the high-water mark instead means the zeroing
happens on a connection's first request and never again — and the
buffer stops relocating mid-decode, which is what the offsets in
`quads` existed to survive in the first place.

<a id="h2-drain-cursor"></a>
### The drain cursor

Where the next round starts walking the stream table. The round is
bounded (it stops when the plan is full), so without a moving start the
first parked stream would take every round until it finished and the
last would wait out all the others. It is a hint, not an index:
`close_stream` reorders the table under it, and a stale value only
costs a different starting point.

<a id="h2-eager-objects"></a>
### Eager per-connection objects, measured

One `H2State` per connection **that spoke the preface**, allocated then
and never before: eager per-connection objects measured **−12 %
throughput and +58 % p99 at 7000 idle connections** on the old tree. An
h1 connection carries one null pointer and nothing else. That
measurement is the standing argument against every per-connection cache
in this tree, and it is cited wherever one is proposed.

<a id="rfc7541"></a>
# RFC 7541 — HPACK

Only the **decoder** is foreign (ls-hpack), which is exactly where the
CVE class of this codec lives. The encoding this tree emits is written
by hand, because without a dynamic table and without Huffman it is
trivial:

- **§5.2** string length: 7-bit prefix integer, H bit 0 — no Huffman on
  the way out.
- **§6.1** indexed field: `:status` rides its static-table entry where
  one exists (Appendix A, indexes 8–14 → 200 = `0x88`, 204, 304, 400,
  404, 500).
- **§6.2.2** literal without indexing, indexed name: 4-bit prefix
  integer. Never-indexed responses keep the blocks
  connection-independent, which is what makes precomputing them legal.
- Static-table name indexes this tree spells by number: content-type
  31, content-encoding 26, vary 59, etag 34, last-modified 44, date 33.
- lsxpack's canonical layout is `name ": " value` in one buffer; the
  `": "` is what `LSHPACK_DEC_HTTP1X_OUTPUT` builds expect between the
  offsets, and it is kept even though this build does not set it.

`SETTINGS_HEADER_TABLE_SIZE` is a documented no-op: an encoder that
never indexes is legal at any table size (§4.2).

`nghttp2_hd` and cashpack were both measured against ls-hpack and both
lost, in decode **and** encode. The codec is not the reason for any gap
between h1 and h2.

<a id="rfc6455"></a>
# RFC 6455 — The WebSocket Protocol

`src/websocket.cpp` is the protocol — bytes in, bytes out, no state, no
IO, no mruby — so it can be driven from a test binary and by Autobahn
without a socket in sight. `src/wsconn.cpp` is the part that holds a
peer: message assembly, the control-frame duties the RFC puts on an
endpoint, and the resource the route named.

**Why this tree writes its own instead of taking a library:** the
framing *is* that one file — a bit test, a length, a four-byte mask —
and every candidate library brought its own event loop, its own
allocator or its own buffer discipline, each of which is a thing this
tree already owns and only owns once.

What `websocket.cpp` deliberately does **not** do: text-frame UTF-8
validation (its caller does it through mruby-string-is-utf8, whose
simdutf validates a whole buffer with SIMD — reimplementing that here
would be the slow variant of a solved problem), and any policy about
who may open a socket (that is the route's).

<a id="ws-handshake"></a>
## §4.2 — the handshake

- **step 5** — the key is 16 bytes base64'd, so 24 characters. Checked
  rather than assumed: the hash below would happily digest anything,
  and a peer that sent nonsense should be told so instead of getting a
  valid-looking accept.
- **step 5.4** — the key, then the fixed GUID: sixty bytes, one block,
  SHA-1, base64 → 28 characters.
- **step 5.5** — at most one subprotocol, and only one the client
  offered — which the resource read out of the head itself.
- **§4.1** — the handshake is a GET and it carries a key.
- **§4.4** — the version this endpoint speaks is 13, and a peer that
  asked for another one is told **which**. That is what makes 426
  useful instead of merely negative.

<a id="ws-sha1"></a>
### SHA-1 and base64 come from libraries

Neither is written here any more, on measured experience: a hand-rolled
SHA-1 was a bottleneck in an earlier tree. The handshake is the only
place this tree hashes anything at all, and §4.2.2 uses SHA-1 as a
fixed transform proving the peer read the request — not as a security
primitive, and it says so itself.

`<openssl/sha.h>` deliberately, and it is not a TLS dependency sneaking
back in: it is **one function** out of libcrypto, which is on every
server distribution, and aws-lc — the crypto library this stack will
bring along when TLS returns through mruby-ktls/s2n — answers the same
API. The day libcrypto here *is* aws-lc, not a line changes.

`SHA1()` is a low-level call OpenSSL 3 marks deprecated in favour of
EVP. Named rather than obeyed: EVP would allocate a context per
handshake to hash sixty bytes, and aws-lc does not deprecate it at all.

Base64 goes through simdutf — the same library that validates text
frames, arriving through mruby-string-is-utf8. Writing it by hand was
six lines and it is still gone: one base64 in the process, and it is
the one somebody else has fuzzed.

<a id="ws-frames"></a>
## §5.1 / §5.2 / §5.3 — frames

- A client-to-server frame **must** be masked; a server frame never is.
- Unmasking happens **in place**: the payload is then the caller's to
  read where it already lies, and no frame is ever copied.
- The minimal number of bytes must be used for the length.
- RSV1–3 must be zero unless an extension negotiated them. RSV2 and
  RSV3 name extensions this tree does not offer, so they are refusals
  for good; RSV1 is permessage-deflate's and is legal exactly while a
  codec exists.
- Opcode gaps are reserved and refused by name.

<a id="ws-fragments"></a>
## §5.4 — fragmentation

A continuation with nothing to continue, and a new message beginning
inside another one, are both errors.

Room is reserved for **this frame**, not for the limit: a 10-byte
message must not allocate what a route allowed at most. A compressed
frame guesses with its own length, which is a floor on what it becomes
and never more than the route allowed.

<a id="ws-control"></a>
## §5.5 — control frames

At most 125 bytes, never fragmented. Both are the **frame** being
wrong, not the payload — refusals, not clamps.

- **§5.5.1 close** — sent at most once, whoever started it.
- **§5.5.2 ping** — an endpoint **must** answer with a pong carrying
  the same payload. That is the endpoint's duty and not an application
  decision, so it happens in C and the resource never hears about it.
- **§5.5.3 pong** — unsolicited pongs are legal and need no answer.

<a id="ws-close"></a>
### The close handshake, and the bug it cost

Our Close goes out and the connection **stays open** until the peer
answers with its own. Tearing the socket down at that moment — which is
what this tree did — shuts the read side while the peer's Close is
still in flight, so that Close lands on a closed socket: EPIPE here,
RST on the wire, and an RST discards whatever the peer had not read
yet. The peer therefore loses the very Close frame it was answering and
reports an abnormal closure (1006) instead of the code the resource
named. A conformant client — every browser — answers, so every browser
saw it.

Nothing more is said from this side (§5.5.1 forbids further data
frames), which is why the message dispatch drops whatever still
arrives. The peer's Close ends the connection; a peer that never
answers is reaped by the idle clock.

**Autobahn cannot see this class of bug**, and that is worth writing
down: the conformance fixture's `on_data` returns only `data`, never a
Symbol, so the application-initiated close branch is unreachable — and
Autobahn never answers a server-initiated close either.

<a id="ws-close-codes"></a>
## §7.1.5 / §7.1.6 / §7.4.1 — close codes

- A zero-length close payload is 1005 "no status" and **not** an error;
  a one-byte payload **is** one, because the code takes two bytes.
- The reason is UTF-8 like any text payload, and shares a control
  frame's 125 bytes with the two-byte code — so 123 is what is left.
  **Truncated, not refused:** a reason is human text, and losing its
  tail is better than losing the close.
- 0–999 are never used; 1004, 1005, 1006 and 1015 are reserved for the
  local end and must not appear on the wire; 1016–2999 is unassigned.
- 1005 is local-only and must not go back on the wire when echoing.
- 1006 is what the RFC reserves for "closed abnormally, no close frame
  was seen" — which is precisely the teardown path, so that is the code
  `on_close` hears there.
- 1009 is the code for a message past `max_message`; 1007 for text that
  is not valid UTF-8; 1011 for a callback that raised or returned
  something nobody can spell.

<a id="ws-utf8"></a>
## §8.1 — UTF-8 in text messages

**True by default**, because the RFC says MUST and Autobahn's whole
section 6 checks it. A route may answer `validate_text? = false`; the
one reason to is throughput on a link whose payloads are known good,
and the price is stated where it is paid — this endpoint then forwards
whatever arrives, and a peer sending broken text gets an answer instead
of 1007.

Validation happens **as bytes land**, not when the message ends.
§8.1 lets a text message be rejected the moment it *cannot* become
valid, and Autobahn 6.4.x tests exactly that: waiting for the last
fragment is correct but late (measured NON-STRICT). So every chunk is
validated as it arrives and only a sequence the chunk boundary cut in
half is carried to the next one.

simdutf answers `TOO_SHORT` both for a sequence a boundary cut and for
a lead byte followed by a byte that can never continue it — and the
difference is the whole of Autobahn 6.4.x: `F4 90` is already
unrecoverable (F4 admits only 80–8F), so a server that waits for the
rest of the message is late. The continuation table from RFC 3629 is
spelled out in this tree because that is the one thing the library
cannot answer.

For a compressed message the UTF-8 check reads the **decompressed**
bytes, which is the only place §8.1 can be asked at all.

<a id="ws-reader"></a>
## The reader: one copy, and no payload buffer at all

The Ring lends fixed 4 KiB buffers, so a message bigger than one buffer
arrives in pieces no matter what — the bytes must be copied somewhere.
The obvious shape (gather into a `std::string`, then build an mruby
String out of it) copies every one of those bytes **twice**. So this
reader keeps no payload buffer: once a frame header is complete, every
payload byte is unmasked and appended straight into the mruby String
that will be handed to `on_data`. One copy, from the pool buffer into
the VM heap, and the pool buffer is never written to.

What *is* buffered is at most 14 bytes of frame header (2 + 8 length +
4 mask) that a receive happened to cut in half, and a control frame's
payload, which §5.5 caps at 125 bytes.

The message String is rooted for as long as it takes — fragments may
arrive over many ticks — with **one registration per message, not per
connection**: a connection between messages holds no Ruby object at
all.

The whole reader runs under `mrb_protect_error`, one protected frame
per receive and not per byte: it builds mruby Strings, and mruby
answers an exhausted heap by **raising**. Outside a VM frame nothing
would catch that, and a websocket's peer must not be able to take the
process down by asking for memory.

<a id="ws-max-message"></a>
### `max_message`

The same question as "how big an mruby String may this layer build" —
every delivered message is one String copied into the GC heap.

The default is small on purpose. A whole message arriving in **one**
frame is never buffered: it goes straight from the receive pool into
that one String, so it costs one copy. A **fragmented** message is
assembled first, so its peak is two copies — and both are **per
connection**, of which there are as many as the derived capacity
allows (tens of thousands). A megabyte times that is not a number a
peer should get to choose.

Which length it bounds differs by kind, and that is the whole
decompression-bomb answer: for a plain message the frame's own length
*is* the message's, so the cap can refuse before a byte is read. For a
**compressed** one it is not — the frame length counts deflate bytes,
and what the message *becomes* is not knowable until it has become it.
So the cap moves to where the bytes appear, inside the inflate sink,
and the compressed side is deliberately left **unbounded**: a peer may
spend all the bandwidth it likes, it may not choose how much of this
process's heap the result takes. A compressed-length cap would refuse
an incompressible 64 KiB message while waving through a 200-byte one
that inflates to a gigabyte.

<a id="ws-resource"></a>
## The resource surface

A websocket route names a `Webmachine::WebsocketResource`, and that
class stands on its **own** — it is not a `Webmachine::Resource`.
Almost nothing of HTTP survives the upgrade: no response, no status, no
flow, no negotiation. What survives is the handshake's **head**, so
that is the one thing a websocket resource can ask for. A base class
that inherited the flow's would have promised all the rest.

It is instantiated **once per connection** and then fed — methods, no
block, no proc:

```ruby
class Echo < Webmachine::WebsocketResource
  def initialize             # optional — THE CONNECT HOOK
    # This object is THIS peer's, so ivars set here live for the whole
    # connection. `request` is live too: the subprotocol, an Origin
    # check, a token in the query are decided from it.
    # nil accepts; a String accepts AND is the Sec-WebSocket-Protocol
    # answer; a Symbol refuses the upgrade with an HTTP status.
  end

  def on_data(data, binary)  # required
    data                     # a String goes back to the client
  end

  def on_close(code, reason) # optional
  end
end
```

`initialize` replaced `on_open`: the resource is built per connection,
so its constructor **is** the connect hook — one concept instead of
two, and the object exists from its first line onward. The object is
allocated and initialized in two steps, because `new` would swallow the
return value and the return value *is* the decision.

Every callback's arity is read **once** at fold: `def on_data(data)`
and `def on_data(data, binary)` are both called correctly, and nothing
is passed that the method did not ask for. mruby's own arity says it —
`n >= 0` means exactly n required, `n < 0` means `-(n+1)` required plus
optionals or a splat, which is a method saying "hand me what there is".

What the method **returns** is the whole protocol between Ruby and this
layer:

| return | meaning |
|---|---|
| String | sent to the client, in the **same kind** the message arrived in — which is what makes an echo `data` and nothing else |
| Symbol | an RFC-relevant answer: a close code by name, or a control frame |
| nil | nothing is said — a callback that only *did* something falls off its own end |
| anything else | 1011, and why on stderr: a return value nobody can spell is a bug in the resource, not a message to guess at |

Three konst answers, asked once at fold and free per message:

```ruby
def self.max_message        = 8 * 1024 * 1024   # default 64 KiB
def self.validate_text?     = false             # default true
def self.permessage_deflate? = true             # default false
```

<a id="ws-session"></a>
### Per-connection Ruby state is the point

A websocket connection **is** a session, so its resource is one object
per peer: `initialize` opens it, ivars carry the session across
messages, `on_close` ends it, and the object is released with the
socket. HTTP went the other way in the same breath — there a resource
lives **one request**, because HTTP is stateless.

What that costs, where it is paid: one mruby object per open websocket,
plus whatever the app's `initialize` builds. The −12 % / +58 %
measurement applies — the difference is that this object **is** the
feature, and only a peer that actually upgraded gets one.

The class is frozen like every routed class: nothing may be redefined
behind an open socket.

<a id="ws-raise"></a>
## A raise never kills the process

A raising `on_data` is a 1011, said once, with the reason in the error
log and on stderr — the connection dies, the server does not. A raising
`on_close` is logged and swallowed: the connection is already over, and
taking the process with it would be the opposite of a close handler.

<a id="rfc7692"></a>
# RFC 7692 — permessage-deflate

The negotiation and the codec, and nothing else — the same cut
`websocket.cpp` makes for the framing, so both halves can be driven
from a test binary before a socket exists.

<a id="pmd-zlib"></a>
## Why the system zlib and not libdeflate

7692 is a **stream**. A message is compressed with `Z_SYNC_FLUSH` and
the LZ77 window is carried into the next one (§7.1.1, *context
takeover*), so the compressor's state outlives every single call.
libdeflate's whole-buffer API cannot express that at all — it is not
slower here, it is **unable**. zlib's `z_stream` is, and `libz.so.1` is
on every server distribution.

<a id="pmd-cost"></a>
## What it costs, in bytes, because that is what decides the default

zlib's own arithmetic (`deflate.c`): `(1 << (windowBits+2)) + (1 <<
(memLevel+9))` for the compressor — 128 KiB + 128 KiB at the defaults —
plus `(1 << windowBits)` + state for the decompressor, about 40 KiB.
Call it **296 KiB per peer**, on a tree whose connection capacity is
derived in the tens of thousands.

That is why the extension is **opt-in per route** (default false) and
why the streams are built **lazily**, on the first message that
actually needs one. The −12 % / +58 % measurement applies here too, and
this object is two orders of magnitude bigger than the one that
produced it.

A route that never negotiates carries one null pointer for the whole
extension — not the 296 KiB, not the pointer's own indirection on any
path it does not take.

<a id="pmd-rsv1"></a>
## §6 — RSV1 belongs to the message, not the frame

So it rides the message's **first** frame. A continuation carrying it,
or a control frame carrying it, is the peer confusing a message with a
frame. That is also why control frames go through `emit()` directly:
§6 forbids RSV1 on a control frame, so there is no branch to get wrong.

<a id="pmd-takeover"></a>
## §7.1.1 — context takeover

Without it, the peer starts every message from an empty window, so this
side must too. A stream that ended (the peer sent a BFINAL block) is
reset either way — nothing can follow a finished deflate stream. When
the client asked *this* side to start fresh, the window goes away
between messages: it is the same `z_stream` — the 256 KiB stays; what
resets is the history the peer's inflater is allowed to assume.

<a id="pmd-window-bits"></a>
## §7.1.2.1 / §7.1.2.2 — the window parameters, and zlib's 8-bit bug

**The smallest window a raw deflate stream can have is 9, not 8.**
`deflateInit2` checks `windowBits == 8 && wrap != 1` and answers
`Z_STREAM_ERROR`, because the 256-byte window has a bug zlib never
fixed. 7692 lets a client name 8 anyway (§7.1.2.1: 8 to 15 inclusive),
and that one fact answers both directions:

- `server_max_window_bits=8` is **declined by name** rather than
  answered with 9 — a response naming a larger window than the offer is
  what §7.1.2.1 forbids, and a response naming 8 while compressing with
  9 would hand the peer a stream its inflater cannot follow.
- `client_max_window_bits=8` is **accepted and echoed**, and the
  decompressor built one bit larger: the client's zlib cannot produce
  an 8-bit window either, so 9 is what will actually arrive. One bit
  larger than promised can only ever be right; one bit smaller would
  fail a stream that is perfectly legal.

Values are 8..15 with **no leading zeroes** — §7.1.2.1 says so in as
many words, so `08` and `015` are refusals and not 8 and 15.

`client_max_window_bits` without a value says only that the client
would *understand* the parameter in the response; the client still uses
15 unless the response names something smaller, and this endpoint names
nothing. With a value, that is what the client would rather use, so it
is echoed and the decompressor is built that small.

Only what was **offered** goes back. The two `no_context_takeover`
parameters are echoed as confirmation — the client promised, and this
endpoint says it heard.

<a id="pmd-four-bytes"></a>
## §7.2.1 / §7.2.2 — the four bytes

A `Z_SYNC_FLUSH` ends the deflate stream with an empty stored block,
and the four bytes that spells (`00 00 FF FF`) are removed by the
sender and put back by the receiver. They are not payload; they are the
frame boundary the extension does not need to repeat.

An **empty** message flushes to exactly those four plus one byte of
empty-block header, so what is left is one byte — the shortest legal
compressed payload, and not a bug.

`Z_SYNC_FLUSH` is done when it stopped needing room: zlib's own
"`avail_out != 0` means the flush completed".

<a id="pmd-negotiate"></a>
## §5.1 — declining is never an error

A server may ignore an offer it does not want, and the connection is
then a perfectly good plain websocket. So the negotiation returns false
for "nothing here", never for "this handshake is bad" — the one thing
that could fail a handshake is a malformed header, and a malformed
extension header is indistinguishable from an extension we do not
offer. §7.1: an unknown parameter, a value where none belongs, or the
same parameter twice makes **the offer** unacceptable, not the
handshake; the next offer in the list gets its turn.

A field may appear more than once (RFC 9110 §5.3 makes a list one field
or many); the **first** offer anywhere in them that this endpoint can
accept wins, which is §5.1's *"the server selects one"*. §9110 5.6.4's
quoted-string form is accepted: 7692's own values are all tokens, but a
client is allowed to quote them and some do.

<a id="pmd-no-floor"></a>
## Every data message is compressed, with no size floor

Deliberately, and the contrast with h1 is the point. `kCompressFloor`
exists in h1 because `Accept-Encoding` is a client saying "I would take
one if you have one" about a body it did not ask for, and below one
segment compression cannot save a packet. Here the peer **named** this
extension in its handshake, and with context takeover the saving on a
**small** message is exactly where 7692 pays off — a 200-byte frame
repeating a schema goes to twenty once the window is warm, which a
packet-counting floor cannot see. The case a floor would win, a tiny
incompressible message, costs the five bytes of an empty stored block.

<a id="pmd-fallback"></a>
## The decision is made before compressing, never after

With context takeover, feeding the compressor and then discarding its
output would leave this side's window holding bytes the peer's window
never saw, and every following message would decode to garbage. So a
failed compress falls back to identity **and** the codec refuses to
compress again — which is a state the peer can follow, unlike a
half-fed one. §6 explicitly allows sending a message uncompressed.

`avail_in` is a `uInt` and has been since 1995. No route's
`max_message` comes near 4 GiB, and the one that did would get a
silently truncated message rather than a refusal — so it *is* a
refusal, and the caller sends the thing uncompressed.

The compression scratch buffer is the **process's**, not the
connection's: one thread, one ring, one message compressed at a time,
so a hundred thousand idle peers do not each hold a buffer sized by the
biggest thing they ever said.

`Z_BEST_SPEED`, the same end of the scale dynamic bodies live at. It
costs less here than there, because context takeover means the
**dictionary** — not the search effort — is what makes a chatty
connection's messages small. `memLevel` 8 is zlib's own default and
stays it: deviating is a ratio-against-memory trade, and this tree does
not publish those without a measurement on real hardware.

<a id="sse"></a>
# WHATWG HTML — server-sent events

Its own route table, like websockets and for the same reason: an SSE
route is matched before the flow or not at all. Nothing of the decision
graph applies — there is no conneg (the media type is fixed), no
precondition (there is no representation to compare), no Content-Length
(the body has no end until somebody ends it).

**What makes it different from every other tier here:** it is the first
source in this tree that produces on **its own schedule**. Everything
else answers bytes with bytes. An event stream is a request answered
once, at the head, and then quiet for as long as the application likes.
So the reactor's own second — the one it already wakes on for the
timeout clocks — is the clock the stream runs on: once a second, per
open stream, the resource is asked what it has. That costs one VM call
per second per stream and not one timer anywhere.

<a id="sse-resource"></a>
## The surface

Deliberately the WebsocketResource one — a stream is a session, so the
same lifetime rule holds. A `Webmachine::SseResource` stands on its
own, is instantiated **once per stream**, and is fed by methods.

```ruby
class Clock < Webmachine::SseResource
  def initialize      # optional — THE OPEN HOOK
    # This object is THIS stream's; ivars live as long as the
    # connection. `request` is live — the head that asked, Last-Event-ID
    # among its fields. nil accepts; a Symbol refuses with an HTTP
    # status and the stream never opens.
    @n = 0
  end

  def on_tick         # required — once a second
    @n += 1
    return nil if @n % 5 != 0     # nothing to say this second
    { event: 'tick', data: @n.to_s, id: @n.to_s }
  end

  def on_close        # optional
  end
end
```

What `on_tick` **returns** is the whole protocol:

| return | meaning |
|---|---|
| nil / false | nothing this second — the stream stays open and costs nothing but the heartbeat |
| String | one event's `data`; a String with newlines becomes several `data:` lines, which is what the spec says they mean |
| Hash | the fields by name: `:data`, `:event`, `:id`, `:retry`. `:data` may be a String or an Array of them |
| Array | several of the above, in one round |
| `:close` | the stream ends here, the connection closes |
| anything else | the stream ends and why is said on stderr — a return value nobody can spell is a bug in the resource |

`:close` is the only word here; anything else is a typo the app should
hear about rather than a message to guess at.

A trailing CR belongs to the line break, not to the value: a Ruby
String that came off a CRLF wire must not put a stray CR into a field.

<a id="sse-heartbeat"></a>
## The heartbeat is the server's, not the application's

A stream that says nothing for long enough is indistinguishable from a
dead one to every proxy in between, so a bare comment (`:\n\n`, which
the spec defines as ignorable) goes out when nothing else has. It
exists for the proxies, which cannot tell a quiet stream from a dead
one. It measures **silence, not events**: the clock is the last second
this stream put *bytes* on the wire, heartbeat included.

The route names the interval as a **duration** through mruby-chrono,
like every other duration that crosses this boundary:

```ruby
def self.heartbeat = 15.s     # default 15 seconds; 0 = never
```

<a id="sse-framing"></a>
## HTTP/1.1 only, refused by name elsewhere

The h1 answer is chunked (RFC 9112 §7.1: each event is one chunk, the
stream ends with the terminal chunk) — the only framing that lets the
connection stay legal without knowing its own length. Every second that
says something is exactly one chunk: the stream's framing and the
stream's rhythm are the same thing, and the terminal chunk makes the
stream end as a well-formed message rather than a dropped socket.

- **HTTP/1.0 gets 505.** It has no chunked and no EventSource, and a
  stream delimited by the connection's end is a message this tree
  cannot frame honestly. Refused by name rather than served badly.
- **HTTP/2 gets 501** for now: an unbounded DATA stream is
  stream-lifetime work that belongs with the h2-bidi task, and
  pretending otherwise would ship a half answer.
- **Anything but GET is 405** with the Allow that says so — a stream
  has one representation and no other method has a meaning here.

The head carries `Cache-Control: no-store`, because a stream is not a
representation anything may keep (RFC 9111 §5.2.2.5), and no
`Connection` header: 1.1 persists by default and this one persists
until somebody ends it.

Whatever the peer pipelined behind the request is discarded with the
carry: this connection is a stream now, and a second request on it has
nowhere to be answered. Whatever it sends *afterwards* is read and
dropped rather than parsed as a head that could never be served.

<a id="rfc1952"></a>
# RFC 1952 / 1951 — gzip and DEFLATE

Two tiers build the **same** wire shape — an RFC 1952 header and
trailer around a raw DEFLATE stream — and they do it separately on
purpose.

<a id="gz-header"></a>
## §2.3.1 — the header, constant because two fields are "unknown"

Magic, `CM=8` (deflate), `FLG=0`, `MTIME=0`, `XFL=0`, `OS=0xff`. MTIME
and OS are both the legal "unknown" values, and they are the only
reason the ten bytes can be a constant at all — a real mtime would make
the header per-entry. The trailer is CRC-32 and ISIZE, little-endian
(§2.3); for an asset both come straight out of the ZIP Central
Directory, so there is **no runtime compression and no decompression,
ever**, on the asset path.

gzip framing costs exactly 18 bytes: 10 header + 8 trailer.

The dynamic-body tier keeps its own copy of those ten bytes rather than
sharing the asset tier's, because sharing would tie a per-request path
to an asset-tier type for ten static bytes that never change.

<a id="gz-dynamic"></a>
## Dynamic bodies: level 1, raw deflate

`Z_BEST_SPEED` — dynamic bodies live at the fast end of the scale only;
zstd -19 and brotli q11 are an asset **build's** job, never a
response's. Raw deflate (`windowBits -15`): no zlib or gzip wrapper
from zlib itself, because the header and trailer above **are** the
wrapper, hand-built the same way the asset tier's is, so both tiers
emit the exact same envelope.

One-shot: the whole body is already in memory (`to_html` returns a
String, never a stream), so there is no reason to hold a persistent
`z_stream` across calls the way permessage-deflate does.
`deflateBound` sizes the buffer for one call to finish the whole input
in a single shot, so anything but `Z_STREAM_END` means zlib itself
refused — not "needs another call", because there is not going to be
one.

A refusal (allocation failure, or input at or above 4 GiB, since
`avail_in` is `uint32_t`) means the caller serves **identity** instead.
Compression is an optimization on top of an always-correct fallback,
never a reason to fail a response: nothing here may 406 or 500.

zlib's `next_in` is `Bytef*` even for input it only reads — the `const`
is missing from the 1995 API, not from the contract.

<a id="gz-media-types"></a>
## Which media types are worth compressing

Decided **once** per resource at setup — the narrow gate lets through a
minority, so a resource outside it costs no branch at answer time, only
one bool.

Structural, not a guess: `text/*` always compresses; anything ending
`+json` or `+xml` is a registered structured-syntax suffix (RFC 6839)
and inherits its base type's compressibility; a short named list covers
the common textual types that are neither — `application/json`,
`application/javascript`, `application/xml`, `application/wasm` (a
binary format, but one deflate reliably shrinks: mostly small integer
opcodes and LEB128, not entropy), and `image/svg+xml` (XML, mislabeled
as an `image/` type by history).

**Everything else, including anything the table has never heard of,
answers false** — conservative downward, because a wrong "yes" spends
CPU compressing bytes that gain nothing (image/png, video/*,
application/zip) while a wrong "no" only ever costs bytes on the wire,
never correctness. Parameters after a `;` are ignored: the media type
answers the question, not what follows the semicolon.

<a id="gz-floor"></a>
## The compression floor, and the kernel finding that forced it

A **fixed floor** replaces the per-connection `TCP_MAXSEG` query this
tree used to make at accept. The kernel would not give that answer
through the ring at all: `io_uring_cmd_getsockopt`
(`io_uring/cmd_net.c`) hard-refuses every level but `SOL_SOCKET`, and
`TCP_MAXSEG` is `IPPROTO_TCP` — structurally unreachable through the
ring by any op, confirmed live as `-EOPNOTSUPP`. The only bridge was
`IORING_OP_FIXED_FD_INSTALL` + `getsockopt(2)` + `close(2)`, linked
ahead of the first recv so the query always landed before a response
could be built — **a whole extra ring round-trip of latency on every
TCP accept, paid before the connection had said a word.**

1280 is the IPv6 minimum MTU (RFC 8200 §5): the floor every path must
carry, and the one a real fleet clamps to in practice (LTE behind a
VPN). One segment's payload at the narrowest legal MTU runs ~1208–1240
bytes, so head+body ≥ 1280 is safely ≥ 2 segments on **every** path —
compression there can only ever save a packet. On a wider path the band
between 1280 and the real MSS spends a little CPU compressing a
response that still fits one segment; that is the **cheap** direction
to be wrong in, chosen deliberately.

This is **not** a return to the old `kAssumedMss = 1460`. That guess
erred the *expensive* way, overestimating the segment and refusing
compression that would have saved packets. A floor errs harmlessly; an
assumed ceiling erred the other way. The two are opposites, not a
repeat.

The first gate before it is whether the transport is **packetized** at
all: a unix listener sits behind a proxy and is never packetized on
this hop, so it never compresses here.

<a id="zip"></a>
# ZIP (APPNOTE) — the asset archive

One fd, one mmap, a table built at `add_route` and never touched again.
Only the Central Directory is read — its sizes are always right, while
Local Header sizes may be zeroed by data descriptors (flag bit 3) —
and each entry's local header is skipped once at setup, never per
request.

The fd is a **setup tool**, closed before setup returns: the mapping
keeps the pages alive by itself, and nothing past setup reads the
archive through a descriptor. One fd fewer against the reserve, and one
fewer thing to own.

<a id="zip-miniz"></a>
## The archive is parsed by miniz, not by this tree

*".zip ist ne riesen Angriffsflaeche, da was selbst zu rollen schreit
danach CVEs zu wollen."* What used to live here was an end record
scanned backwards over 64 KiB, 46-byte central directory rows with four
variable-length fields each, Zip64 escapes, an encryption flag, and a
bounds check against the mapping behind every one of them — **137
instrumented edges of hand-written foreign-format parsing**, which is
the shape every ZIP CVE has ever had.

<a id="zip-libzip"></a>
### Why miniz and not libzip

The standing rule would prefer libzip (a stable ABI every distribution
carries), but **libzip cannot answer the question this tier asks.** It
hands over *bytes* — `zip_fopen_index` plus `zip_fread` — and has no
public API for an entry's **position**
(`zip_source_seek_compute_offset` is a helper for source
implementations, not that). Taking it would mean copying every served
byte into an arena at setup and losing the mapping: file-backed pages
the kernel faults in on demand and can evict would become anonymous RSS
that must all stay resident. The delivery model — an iovec into the
mapping, one sendmsg, no copy — is not something to trade for a
packaging preference.

miniz answers it: `mz_zip_reader_init_mem` parses **our** mapping with
no IO at all (`MINIZ_NO_STDIO` is a first-class build switch, not a
workaround), and `mz_zip_archive_file_stat` carries
`m_local_header_ofs` — a position — next to the metadata HTTP needs:
`m_comp_size`, `m_uncomp_size`, `m_crc32`, `m_method`, `m_time` as a
`time_t`, `m_is_directory`, `m_is_encrypted`, `m_is_supported`.

**What this tree still reads of the format, and it is the whole of it:**
the 30-byte Local Header, to skip it. Its name and extra lengths may
differ from the directory's, so they must be read locally — a signature
check and two `uint16` at +26 and +28. Five lines against the directory
walk that is gone, and the result is bounds-checked against the mapping
like everything that indexes into it.

<a id="zip-method"></a>
## The ZIP method encodes the delivery decision

Method 8 (deflate) is served as `Content-Encoding: gzip` — a method-8
entry **is** a raw deflate stream, i.e. exactly the body of a gzip
response, and the two fields the gzip trailer needs (CRC-32,
uncompressed size) sit in the Central Directory. Method 0 (stored) is
served as identity. One field compare at runtime: no table, no
heuristic, no percentage.

An old rule said "never infer the coding from the method". It held when
method 0 was ambiguous — identity *or* brotli in a `.br` sibling entry.
With **one** entry per file and no siblings, method 0 is unambiguously
identity, and the inference is exactly right.

<a id="zip-deflate-only"></a>
## Why only deflate (final)

The file must survive the Windows Explorer — open, read, **and**
change. Explorer writes deflate and cannot be taught stored or zstd,
and it cannot keep sibling entries in sync. With one deflate-or-stored
entry per file, an Explorer edit degrades cleanly (a replaced JPEG
becomes method 8 and ships as gzip: wasteful, correct, fixed by the
next build) instead of breaking.

**Zip64 is excluded, not postponed** — Explorer's Zip64 support is
historically bad. Under 65535 entries and under 4 GB is a requirement,
refused by name at setup. Encryption and unsupported methods are
miniz's own findings, restated in this tier's words.

<a id="zip-traversal"></a>
## Path traversal is structurally impossible

Not filtered: a request can only name what the table holds. The
request-target has its query stripped, its leading slash dropped, and
the rest must equal a table name **byte for byte** — no
percent-decoding, because entries are named by their table row and not
by an escape grammar. No `..`-parsing, no `realpath`, no CVE class.

A duplicated name keeps its **last** directory row — the row a
rewriting tool appended most recently.

<a id="zip-mtime"></a>
## The archive's mtime

miniz has already read whichever of the DOS date/time fields
(APPNOTE 4.4.6) or the extended-timestamp extra field the archive
carried, and hands over a `time_t` — so the bit arithmetic that used to
live here went with the parser. The zone is unknowable for a DOS date
(they are "local" with no zone recorded); read as UTC, which every tool
in the chain also pretends. Zero means "no date recorded" and serves no
`Last-Modified`.

<a id="zip-verdict"></a>
## The asset tier's whole decision, in the graph's own order

Conneg before preconditions, C..F before G..:

| status | when |
|---|---|
| 405 | anything but GET/HEAD (501 for methods the tree cannot name) |
| 406 | method-8 entry, Accept-Encoding present, gzip not acceptable |
| 412 | If-Match present and the strong comparison fails |
| 304 | If-None-Match matches (weak comparison) |
| 200 | otherwise |

Prebuilt heads are patched with the date **lazily**, at answer time: a
per-second sweep over thousands of entries would be work nobody asked
for, and an entry nobody requests is never patched. 412 and 501 stay
with the caller's shared status store — they carry nothing
asset-specific.

<a id="zip-mime"></a>
## Media types come off the machine, not out of this source

A media-type database is something the operator installs and curates,
and a table kept in this source could only ever be a worse, staler copy
of it. First that exists wins:

1. the path the operator named (`[server].mime_types`, `--mime-types`)
2. `/etc/mime.types` — Debian media-types, Fedora/Arch mailcap
3. `/etc/apache2/mime.types`, `/etc/httpd/conf/mime.types`,
   `/usr/local/etc/mime.types` — Apache per distro, BSD
4. `/usr/share/mime/globs2` — shared-mime-info
5. the list compiled in (`share/mime.types`, Apache httpd's own,
   Apache-2.0 like this tree)

A path the **operator** named and that cannot be read is a refusal, not
a step down the list: they named it on purpose. The startup says which
source answered, so nothing reaches into a file nobody expected.

Two parsers, because there are two formats: `type ext ext ...` for
1–3 and 5, `weight:type:*.ext` for globs2. nginx's block form stays
out — an operator who has one names it through source 1. An operator's
own file is read as whichever format its **name** says; globs2 is the
only one with a distinct format and it is always called that.

In globs2 only `*.ext` is taken — a glob with any other wildcard names
a whole filename pattern, and this table is keyed by extension. The
weight is read and ignored: the file is already sorted by it, so a
later row for the same extension is the weaker claim and loses to the
earlier one at dedup time.

The table is sorted for binary search and deduplicated so one extension
holds one type. `std::stable_sort` keeps the file's own order among
equal keys, which is what makes "the first row wins" mean "the first
row **of the file**" — globs2's weight ordering and a mime.types
duplicate both resolve the same way.

<a id="beyond"></a>
# Beyond the RFCs

Everything below serves no RFC. A function whose header names one of
these domains has its reasoning here.

<a id="ring"></a>
## The reactor

One thread, one io backend, every piece of state hung off one instance
— no globals, so N instances could exist someday, though no line knows
about threads. **No locking, ever**, follows from that and not the
other way round.

The Ring knows **nothing but bytes**: bytes arrive, it hands them to
its App; whatever the App appends to the sink goes back out. HTTP,
Ruby, echo — all of that lives in an App type bound at compile time
(template, zero indirection, no `std::function`, no `virtual`).

<a id="ring-app"></a>
### The App contract

| member | meaning |
|---|---|
| `Conn::reset(listener, packetized)` | per-connection state. `listener` is the App's key to "whose connection is this"; `packetized` says whether that listener is TCP |
| `feed(Conn&, data, len, sink, Plan*)` | false = close once the sink has drained. The Plan is **nullable**: passed only when it could be armed in this very round |
| `pending(const Conn&)` | does this connection still owe bytes? Asked before each send, so a small head can carry MSG_MORE |
| `more(Conn&, sink, Plan&)` | the delivery continuation: called when the sink has fully drained |
| `timed(const Conn&)` | does this connection carry a source that produces on its own schedule? |
| `on_tick()` | once per reactor wake |
| `access_log()` / `error_log()` | the App formats, the Ring flushes |

<a id="ring-setup"></a>
### Everything goes through the ring

The listener is born as a direct descriptor
(`io_uring_prep_socket_direct`), bound and set listening by ring ops
(`IORING_OP_BIND` / `LISTEN`, kernel 6.11+ — probed at init, named
error if absent, **no POSIX fallback**: one implementation, one path).
The only classic syscall left is `mmap`, which is memory, not IO.

One listener is one linked chain: a stale unix path is unlinked first
and **unlinked from the chain** (a linked op that fails — and ENOENT is
normal there — would cancel everything behind it), then socket →
(setsockopt) → bind → listen as one chain, one submit, every CQE
checked, a failure naming its stage. `-ECANCELED` names the victim of
an earlier failure, not a cause.

Only ENOENT is ordinary on the unlink; anything else on the path is a
refusal. Only a bind that happened leaves a path to remove again.

Port 0 is legal — "the OS picks" — and the pick is read back off the
**bound** listener with the local form of the same
`SOCKET_URING_OP_GETSOCKNAME` the accept path rides. An earlier slice
refused port 0 because "io_uring has no getsockname"; the cmd exists
now and this is its second customer. A kernel without it turns **only**
a port-0 ask into a named refusal — fixed ports never ask the question.

The addresses live on the caller's frame, and init blocks until the
chain's CQEs, so the borrow ends before the frame does.

The listen backlog is 511 — the shared default half the servers on the
net use (nginx's own). `somaxconn` still caps it silently, which
`tools/webmachine-tune.sh` points out on the machine itself.

<a id="ring-tag"></a>
### user_data

`kind(8) | gen(16) | idx(32)`. The generation guards a reused slot
against CQEs of the connection that owned it before. The setup chain's
stages ride in the idx half, so a failing CQE can name what failed.

<a id="ring-capacity"></a>
### The connection table is derived, never guessed

A connection's id **is** its direct descriptor index, so lookup is an
array index. The listeners live in the slots behind the connections.

The count comes from `RLIMIT_NOFILE`: soft is raised to hard at init
(unprivileged, allowed for every process; systemd's default is soft
1024 / hard 524288, and the ceiling for the raise is
`/proc/sys/fs/nr_open`), and the capacity is everything the final limit
allows minus a reserve. The kernel checks the sparse table size against
`RLIMIT_NOFILE` — measured: limit 1024 → 1023 slots ok, 4096 EMFILE —
which is why the raise must come **first**.

`max_conns = final_limit − kFdReserve − kMaxListeners`, one arithmetic
with two consumers: the server sizes itself with it, and
`tools/webmachine-tune.sh` only prints it. The reserve covers classic
fds the process keeps next to the fixed table — stdio, the ring fd, the
stop signalfd, the asset ZIP, and foreign in-process code
(mruby-c-ares sockets). Connections consume no fd numbers under the
real ring, so it is headroom rather than arithmetic necessity; under
the select shim, where connections **are** process fds, the same
formula holds and the reserve becomes load-bearing.

`IORING_MAX_FIXED_FILES` is the kernel's own cap on a fixed-file table,
and a limit above it must not size the table.

`RLIMIT_MEMLOCK` is raised the same way, once, before the ring exists —
a ring's SQ/CQ pages are locked memory accounted per user. Failure is
deliberately **silent**: not being allowed to raise it is no reason not
to start, it only means the ring settles smaller.

<a id="ring-sq"></a>
### The SQ ring: halve until one takes

The SQ is a **shared, fixed** resource — every in-flight operation of
every connection sits in it, and one response can claim many. 32768 is
`IORING_MAX_ENTRIES`; the SQ array costs 64 bytes an entry and the CQ
16 at twice the count, so the full ask is ~3 MiB once per process.

A machine that will not give that gets **less, not a refusal**: a
smaller ring is smaller headroom, not a wrong ring — the same rule that
governs the connection capacity. Halve until one takes; the floor is
what stood before the loop existed, so this can only ever end at least
as well as it used to. A **configured** ask below the floor *is* the
floor for this run: the operator asked for a small ring on purpose, one
try, named refusal if the machine will not give even that.
`queue_init_params` writes its result into the params, so a retry
starts from a clean one.

`register_ring_fd` saves one fd-table lookup per `enter(2)`; nothing
else shares that fd.

The direct-descriptor allocator's cursor continues past the last slot
it touched, so after the listeners land the next accept would be handed
a **listener** slot (measured: `res = 4097`). Allocation is confined to
the connection slots; listeners are **placed**, never allocated.

<a id="ring-no-pin"></a>
### Never pin this process

Measured twice, lost twice. The older tree deleted every `taskset` it
had — handing the scheduler one core was slower than letting it choose;
a client mask widened 2 → 15 → 30 cpus raised throughput monotonically
in the median. And whenever io_uring hands work to an io-wq worker,
that worker **inherits the issuing thread's affinity**: pinning locks
the pool that exists to use *other* cores onto the core the loop
already occupies. Measured at its worst, back when file bodies went
through splice: **0.07×** under `taskset -c 0`, the system at 49.3 % sy
against 10.3 % us.

Buffer-pool geometry was measured in the old tree as not moving the
profile (2048 × 4096 against several ladders: a null result), so the
simple shape stays.

<a id="ring-bundles"></a>
### WM_BUNDLE — the one env knob left, and only ever narrowing

Recv bundles default to the kernel's own feature bit. One known-broken
kernel (container `6.18.5-fc`) violates the dense-fill contract — `res`
spanned buffers each holding only its own small segment — and needs
`WM_BUNDLE=0`. It earns its place by answering a correctness question
no build-time check can.

The buffer ring is written once; replenish is **advance-only**, because
the kernel consumes entries strictly in ring order, so re-exposing a
slot re-exposes the buffer it has always named. Kernel-supplied values
are checked before use: an id or length past the pool would hand out
someone else's memory. Walking a bundle means consecutive ids from
`bid0`, every buffer full except the last — the dense-fill contract
`io_uring_prep_recv(3)` states.

**ENOBUFS is reachable by arithmetic**, not by accident: every
completion consumes at least one whole buffer no matter how few bytes
it carries, and under `DEFER_TASKRUN` all completions of a wait window
are produced before userspace runs again while buffers only return at
the *next* tick's advance. So more readable connections in one window
than the pool has buffers drains it and the rest post ENOBUFS —
without a re-arm their multishot is dead and the connection hangs.

<a id="ring-backend"></a>
### Which backend, and how that is decided

Settled at **build** time: the real liburing, or slipstreamIO's
`select(2)` shim where io_uring is forbidden to the process
(`kernel.io_uring_disabled=1|2`, Docker's seccomp default, SELinux /
AppArmor). There is no second one in the binary to fall back to.

Which of the two capacity paths runs is decided by a **property** the
`liburing.h` on the include path states, never by which implementation
it is: `IO_URING_FD_CEILING` means "every descriptor handed to these
functions must stay strictly below this number", and its absence means
the API imposes no ceiling. Asking *who* answered instead would hand
select's `FD_SETSIZE` to every implementation that comes later — an
IOCP build has no `fd_set` at all — so this file never learns a name.

- **Ceiling stated:** a connection *is* a process fd, and the rlimit is
  the only thing keeping fd numbers under that roof — for this process
  and for every neighbour holding an `fd_set`, mruby-c-ares being the
  concrete one. The soft limit is moved **to** that roof, down where it
  stood higher and up where it stood lower, so the two agree once at
  init.
- **No ceiling:** connections live in the fixed-file table and consume
  no fd numbers, so take everything the hard limit allows.

Whether io_uring is usable **on this machine** is a runtime question
and stays one: a binary built against the real liburing can still land
on a kernel too old for the ring ops, or under a seccomp profile or
sysctl that blocks them. It is not asked twice — mruby-io-uring probes
during `mrb_open()` and publishes `URING_AVAILABLE`; asking again with
a probe of our own would create a second answer that can disagree with
the first.

When the start is refused, the message says **which** reason, when the
machine will tell us: `kernel.io_uring_disabled` (Linux ≥ 6.6, and what
a hardened Debian/Ubuntu ships) is the one an operator can act on — 1
means only members of `kernel.io_uring_group` may, 2 means nobody may.
Anything else leaves the file absent or at 0, and then the general
sentence is the honest one.

Every failure at init is **this machine refusing this configuration** —
a taken port, an fd limit that leaves no room. Nothing in there is a
reason to go looking for another backend: a bind clash that silently
demoted the server to a slower path would be a performance cliff
wearing a startup message.

<a id="deliver"></a>
## Delivery: a source hands over a plan, not a byte

One round's output is **segments**. A segment is either bytes that
already exist somewhere stable — a mapping, a table built at
`add_route` — or a **range of the sink**. h2 needs both, alternating: a
9-byte DATA frame header out of the sink, that frame's payload straight
out of the mapping, again and again.

The sink is a `std::string` the round is still appending to, so its
address is not knowable while the plan is built; the **offset** is. The
Ring resolves it when it arms the send, by which time the sink is final
and nothing more will be appended. A plan that names any sink range
describes the round's sink **completely**; one of pure pointers leaves
the sink to be sent ahead of it — the prepend shifts the array by one,
and the iovec array reserves that slot. Truncating instead would drop
bytes off the wire silently, which is the one failure this model must
not be able to have.

`Plan::Seg` is bare POD and callers write `Plan p;`, not `Plan p{}`:
only `[0, nseg)` is ever read, and value-initializing the array would
memset 3 KB on **every** continuation — `more()` runs after every
drained send, on hello as much as on a transfer.

<a id="deliver-capacity"></a>
### The round's only bound is segment capacity

There is **no byte budget on top**. A round carries as much as there is
work and window, and how much of it the socket takes is not guessed at:
the kernel keeps what fits in the sndbuf and the short write says so,
exactly the way `-ENOBUFS` speaks for the recv buffer ring.

Asking first was measured and buried: `sndbuf − SIOCOUTQ` overclaims by
up to **2.4 %** on a big buffer and **underclaims — negative
remainder** — on small ones, because `tcp_sendmsg` admits by
`sk_wmem_queued`, overshoots `sk_sndbuf` by design, and `SIOCOUTQ`
counts payload only. A number without a stable sign cannot be
margined.

**The capacity number is IOV_MAX's, not ours:** 1023 plus the Ring's
prepend slot is exactly the 1024 iovecs one `sendmsg` may carry (Linux
`UIO_MAXIOV`). The kernel's ceiling is the capacity; nothing invented
sits below it. It has to be that large because a `-m32` batch of
**medium** bodies must fit one round: at 128 segments a 256 KiB
response cost ~33 segments, so a 32-stream batch was cut into 8 rounds
where the old inline copy had needed one — forgecore measured that cut
as **−26 %**. A 4 KiB gzip response is 4 segments, so 32 of them sat
exactly *at* the old 128 and split into two rounds: **−15 %**. That was
the second round-count regression in this file's history; the first was
a byte budget.

h1 has no framing inside a body, so its transfer is at most three
segments however large the body — capacity never cuts it.

<a id="deliver-byte-cap"></a>
### The byte cap, from the socket's own books

`SO_MEMINFO`: sndbuf minus what is queued, the same arithmetic
`sk_stream_wspace` uses. `SO_MEMINFO` is `SOL_SOCKET`, which is exactly
why it works where `TCP_INFO` does not — io_uring's getsockopt cmd
refuses every level but `SOL_SOCKET`. TCP admits against `wmem_queued`,
datagram-style sockets (unix included) against `wmem_alloc`, so the
larger of the two is the honest "used" on either family.

A round built within the cap is accepted inline by the kernel; one
built past it short-writes and then **waits** — a full TCP socket
signals writability only at one-third free, so the remainder sleeps out
a third of the buffer's drain. Measured: 1 MiB responses at 8 MiB
rounds ran at **0.6×** their 1 MiB-round speed on forgecore, **0.3×**
in the container. The cap is soft: overshooting by one frame is a race
the short write corrects, not a fault. Below the floor the floor is
sent anyway — the socket is full and the ring's own poll is the right
waiter; a shorter round would only add beats to the same wait.

Both fixed alternatives were tried and lost: 64 KiB a round multiplied
sends (**−14.5 %** on forgecore), unbounded slept out the one-third
wake past the sndbuf.

A recv processed between a send's CQE and the meminfo CQE may have
armed a new send already — `out` is then the **kernel's**, and
continuing there would arm it a second time. Measured as h2 frame
corruption: duplicated bytes, 30 req/s of retries.

<a id="deliver-warm-budget"></a>
### The warm budget

At or below it a body is **copied** into the response buffer and leaves
with its head in one append; above it the body becomes a source, handed
over as pointers a round at a time. It is one delivery round — a
structural line rather than a tuned one: a body that fits in a single
round has nothing to gain from being a source, because the head would
have to leave on its own first and there is no second round for that to
amortise over.

**The measurement this replaced is worth keeping.** The older tree put
the crossover at 4 KiB and this one carried it over, which produced a
32 KiB collapse on forgecore (**0.22×**). The cause was not the budget:
bodies above it went through `splice`, and splice was being compared
against a path that copied **twice** (mapping → buffer → socket).
Against the pointer path splice loses at every size:

```
forgecore, -t4 -c400, splice against the same server without it
    4 KiB  0.99x    32 KiB  1.01x   256 KiB  0.63x    1 MiB  0.79x
```

So splice is gone, and what remains is one kernel copy out of the
mapping — which is also what makes this budget a small number rather
than a tuning surface.

<a id="deliver-page-line"></a>
### Small pieces are copied, large spans stay pointers

Below one page a piece is copied into the open sink run instead of
becoming an iovec of its own: the kernel pays a setup-and-walk cost per
iovec that a small memcpy undercuts. A 4 KiB gzip response is three
tiny pieces (10-byte header, ~1.9K deflate, 8-byte trailer), and as
three iovecs it measured **14 % slower** than its stored twin's one.

**The value is bracketed by two measurements, same host, same day:** a
4096-byte span is faster as a **pointer** (1.42M req/s against 1.30M
when an 8192 floor copied it); a ~1.9K deflate span is faster
**copied** (its response rose 1.79M → 1.87M when it stopped being three
iovecs). The crossover sits between; one page is the natural line, and
strictly below, so a 4096 piece stays a pointer. The 18 % memmove this
tree removed came from 64 KiB pieces — large spans, which stay
pointers.

<a id="deliver-msg-more"></a>
### MSG_MORE, not TCP_CORK

A response is head-then-body, and a lone small head goes out and then
**waits** for the peer's delayed ACK before the body may follow.
Measured in the previous tree: **44.30 ms average, 1,118 req/s →
31,077 once fixed.**

`MSG_MORE` rather than `TCP_CORK` deliberately: cork is connection
state that needs an uncork afterwards, so a response failing between
head and body would leave the connection corked. `MSG_MORE` is an
argument to one send and cannot outlive it.

`TCP_NODELAY` for the same family of reason: a server that writes
complete responses has nothing for Nagle to coalesce, only stalls to
offer. Found the hard way — a response whose tail went out as its own
small segment waited ~43 ms for the peer's delayed ACK, once per
response.

<a id="deliver-splice-pages"></a>
### MSG_SPLICE_PAGES was tried here and does nothing

Measured on 6.18 through io_uring. It is an
`MSG_INTERNAL_SENDMSG_FLAGS` bit meant for in-kernel callers whose
iterators are already bvec/kvec; a userspace iovec does not qualify.
2 GiB in 256 KiB chunks over loopback, flag on against flag off, three
rounds each: **2001 / 2025 / 2147 MB/s against 2158 / 2064 / 2080**,
with system time equal to three decimals — no saved copy, in either
direction. A second probe confirms it from the other side: clobbering
the source buffer immediately after `io_uring_submit` still puts the
**original** bytes on the wire, i.e. the copy already happened.

Which is the standing rule for every send here: anything that fits in
the sndbuf (3.76 MiB on loopback TCP, 208 KiB on AF_UNIX) is the
kernel's the moment submit returns.

That leaves **one** kernel copy per body and nothing to remove. Both
alternatives cost more than they save and are closed: splice needs a
pipe, a second operation and an io-wq hop (0.63×–0.79× at 256 KiB /
1 MiB); `SEND_ZC` buys the copy back with a `ubuf_info` and a **second
completion per send**, and caps in-flight bytes at the
`RLIMIT_MEMLOCK` account (~8 MB) — a great deal of bookkeeping around a
small window.

<a id="deliver-two-buffers"></a>
### Two buffers, not one

`out` is **borrowed** by an in-flight send (its pointer is in the SQE),
so nothing may append to or clear it until that send's CQE — appends
land in `next`, and the swap happens when the send drains. Capacity
survives `clear()`, so a warm slot allocates nothing.

The iovec pair lives **on the heap, lazily**: at 1024 entries the pair
is 32 KB, and the connection table holds `max_conns` slots (easily a
million). A connection that never hands over a plan — every idle one,
every hello — pays two null pointers; the first plan allocates once and
the block stays for the slot's lifetime.

<a id="ring-close"></a>
### Closing a connection

The armed multishot recv holds a file reference: `close_direct` alone
only clears the table slot, the socket stays open and the peer never
sees FIN — **three bintests hung exactly there.** `shutdown` forces the
FIN out first and the link keeps the order; both SQEs must ride the
same submission or the link breaks. If the linked shutdown fails (the
peer reset first) the close is still owed, or the direct slot leaks.

An in-flight send borrows `out` and the plan's pointers, so the slot
may not be reset — and the descriptor not closed — until its CQE lands.

<a id="ring-clocks"></a>
## The timeout clocks

Three, in seconds, the numbers every server converged on:

| clock | meaning | default |
|---|---|---|
| header | **total** for a request head — the Slowloris brake | 60 |
| send | between wire progresses (nginx's `send_timeout` semantics) | 60 |
| idle | keep-alive quiet time | 75 |

75 is nginx's "we talk to browsers directly" number; Apache's and
Node's 5 is the behind-a-proxy world.

Transitions: accept and idle→first-byte set `now + header`; **later
recvs deliberately do not extend it** — that is what makes it total, and
what makes it a Slowloris brake. A send's progress sets `now + send`. A
full drain with nothing owed sets `now + idle`. Priced at one store on
paths that already run.

**A known edge, stated and not hidden:** a peer that only ever *sends*
— a streaming upload, a websocket client that pushes and never hears —
dies at the header clock unless the server writes something back within
it. Revisit when bodies get a consumer.

The reaper runs once a second, one compare per live connection: at the
derived maximum that is thousands of compares a second, which is noise,
and it is exactly the cost a slow connection may impose on the fast
ones — a bounded, counted one. It runs **after** the batch, so work
that just happened has moved its deadline. A timed source is asked
there and the idle clock does not own it — silence is what an event
stream mostly is. While a send is in flight a connection is left alone:
the send deadline owns it then, and a peer that stopped reading is
still a peer that gets reaped.

The **stuck-send** case: the SQE is parked on a peer that reads
nothing, so waiting for its CQE waits forever. `shutdown` breaks it —
the send completes with an error and the send handler finishes the
close. Once: a flag remembers.

Even without a budget the wait is bounded to a second, because the
clocks need a wake when **nothing** completes. An idle server wakes
once a second, which is the whole cost of having deadlines at all.
`-ETIME` is the clock doing its job, not a failure.

<a id="ring-tick"></a>
## The bounded tick

`Webmachine.tick(budget)` bounds the **work**, not just the wait: the
wait is at most the budget *and* the batch is interrupted between
completions once it is spent. What is left stays in the CQ and the next
tick continues it — the advance only ever released what was **handled**,
so the next tick reads it as if nothing had happened. Between
completions, never inside one: a half-handled CQE has no resumable
state.

The deadline is read **once** and compared between completions against
`CLOCK_MONOTONIC_COARSE` — a vDSO read, no syscall.

`Webmachine.fd` is what an embedder polls between ticks: readable
exactly when the ring has completions to hand over, so an idle server
costs its host nothing. A backend whose completions are not a
descriptor cannot be polled, and pretending otherwise would hand the
embedder a number that never becomes readable.

<a id="ring-drain"></a>
## Drain, then forget

The listeners close at once — nothing new is taken — and the loop keeps
turning until either the last accepted connection is gone or the grace
runs out, whichever comes first. Grace 0 means the second condition is
already true, which is the immediate stop.

The connections that survive the grace are **forgotten, not waited on**:
an idle keep-alive peer that says nothing would otherwise hold the
process open forever, and it is the destructor's ring exit that ends
them — one place, the same place a signal's stop uses.

It is process-wide, and the name says as much: there is one ring and
one loop, so a second application's connections stop with the first's.
`Application#stop` is that same method under webmachine-ruby's
spelling, not a second narrower one — a per-app stop would have to mean
a listener closing while the loop kept turning, which nothing has asked
for and which this would only pretend to do. It never *builds* the
server: stopping one that was never started is a no-op with nothing to
drain.

The listeners leave through the ring like everything else, and the
close is **idempotent** — closing a slot twice would take a slot a
later accept was given. A unix listener takes its path with it, waited
on, because `queue_exit` would race the unlink. The ring's destructor
is what unlinks, so it must run before the process leaves — not at
exit, when nothing is ordered any more.

The stop signal arrives as a **CQE** like everything else: TERM and INT
are blocked and land in a signalfd the ring polls. A handler flag would
race the wait — flag checked, signal lands, wait blocks forever with
the flag set.

<a id="mruby"></a>
## mruby: the VM as a guest

<a id="mruby-two-kinds"></a>
### Two kinds of method, by declaration

| declaration | when it is asked | what it becomes |
|---|---|---|
| `def self.x` — class method | **once**, at `add_route` | konst: folded into the compiled vectors |
| `def x` — instance method | on **every** request | runtime: answered through the VM, inside one frame |

Konst resources never see the VM at all.

<a id="mruby-run-frame"></a>
### The run frame is the memory model

The runtime tier runs the **whole flow** inside one VM method, carried
by a hidden class — no constant names it, so Ruby code can neither
reach nor reopen it, and its cfunc finds the C-side `Resource` through
the proc's env as a `cptr`, never through `mrb->ud` (that slot belongs
to the embedder ecosystem; mruby-io-uring lives in the same process).

Within that frame `mrb->jmp` is armed and the arena lives until exit,
so callbacks are naked yields, values one callback returns stay alive
for the next one **in the arena** (cheaper than any ivar), and the
rendered body is copied out while the frame still roots it.

A per-node-entry variant measured **26 ns faster** on one callback
(forgecore 230 vs 256 ns) and was removed anyway: it cannot host
cross-callback lifetimes without ivars.

<a id="mruby-lifetime"></a>
### Resource lifetime: one request

HTTP is stateless, so its resource is: the run frame builds the object,
the request's callbacks share it, and it dies with the frame. Ivars are
therefore **request** scope — what one callback of a request leaves,
the next callback of that same request finds, and no other request ever
sees it. webmachine-ruby instantiates per request for the same reason;
this tree did not, and cross-request state could leak between
strangers.

**Application** state lives where application state belongs: a mutable
object a constant names, or a global — never a class ivar, because
`add_route` **freezes** the class.

Cost, stated: one object allocation per dynamic request, plus
`initialize` if the class defines one. The konst tier pays nothing.

The freeze is the load-bearing part: from `add_route` on, no method can
be redefined, so every `mrb_method_t` resolved at setup stays true
forever. The class is frozen; instances are not.

<a id="mruby-resolve"></a>
### One resolution, one call path

- `mrb_method_search_vm` on the class's own table answers "is this an
  instance method" — no funcall, no `method_defined?`. It scribbles on
  the class it is given, so it is always given a copy.
- An **alias** (`alias_method` in a class body) stores a proc carrying
  `MRB_PROC_ALIAS` whose body holds the aliased-from mid, not an irep;
  `vm.c` unwraps that at every call site. It is unwrapped **once** here
  instead — the chain is fixed the moment the class freezes.
- A resolved Ruby proc is entered **directly** via
  `mrb_yield_with_class`, skipping the funcall machinery. A cfunc or an
  undef falls back to `mrb_funcall_argv`, with the documented reason:
  reproducing `vm.c`'s frame setup is not worth owning.
- The callback is lent **its own name**: `yield_with_class` fills the
  new frame's mid from the *current* frame for a plain def, and `super`
  resolves through `ci->mid`. Restored after; on a raise the unwind
  pops past the frame and the value is moot.
- Every symbol is a **compile-time presym** — the build scans the
  source — so nothing is interned at runtime; names ride along solely
  for error text.

<a id="mruby-protect"></a>
### Setup calls run under protection, request calls do not

Outside a VM frame nothing catches a raise: `funcall` builds its own
TRY, `yield` does not. So setup-time invocations go through
`mrb_protect_error`, and the request path relies on the wrapper
funcall's TRY instead. The same distinction governs the websocket
reader (one protected frame per receive) and the `ready` hook (called
from the tool, outside any frame, so `Proc#call` and not `mrb_yield`).

<a id="mruby-exception"></a>
### With an exception pending, no funcall

The VM is not in a state to run Ruby. `RException.mesg` is read
**straight from the field** (`mruby/error.h`: "NULL or probably
RString") — calling `#message` there is asking for a second failure on
top of the first. The exception roots the message while pending, and
the caller copies before any mruby call can run, so clearing `exc` is
safe: no allocation happens in between.

The error log's backtrace is the same rule: `mrb_exc_backtrace` is the
C entry mruby's own printer uses, and what it hands back is an Array of
plain Strings. The join allocates, deliberately — this runs when
something already went wrong, which is the one path in this tree that
has no throughput to protect.

Two declarations are borrowed from `mruby/internal.h`, which is a C
header with no `extern "C"` wrapper — including it from C++ yields a
mangled symbol nothing defines. `mrb_proc_arity` and
`mrb_exc_backtrace` are therefore declared next to the one place each
is used.

<a id="mruby-lend"></a>
### The lend contract

Borrowed bytes live **until the next lend**. The rendered body, the
exception's message, the request view: each is valid until the next
one, which is exactly as long as the caller needs — every caller copies
into the sink immediately. That is why there is no `end()` call and no
arena parameter: the API is smaller for it, and the cost is one dead
body String held in the arena between two dynamic requests.

<a id="mruby-chrono"></a>
### Durations cross the boundary through mruby-chrono, and nothing else

One convention for every timeout this tree will ever take — which is
also why `0.5` is a correct half second rather than a parse error, the
API reading Integer and Float alike. Counts are **not** durations:
`backlog` and `sq_entries` stay integers, because a count is not a
duration. Wall-clock time is not a duration either: the date patch
stays plain C.

The target is seconds because that is what the ring can **enforce** —
the deadlines are whole seconds and the reaper runs once a second. A
sub-second ask is rounded **up**, never down: the one direction that
cannot cut a connection earlier than the operator asked for.

<a id="mruby-request"></a>
### The request object is lazy, and there is one of it

There is **one** request object in the process, a hidden Data handle
rooted at init; per request the C side swaps the **view** it points at,
which is a pointer store. Every accessor materialises its Ruby value
when it is **called** and never before, so a resource that asks nothing
allocates nothing, and a konst resource does not even pay the pointer
store.

Nothing memoises across calls: the callback's own frame roots what it
received, and a second call materialises again. That is the same
lifetime rule the rendered body lives under, and it is why the object
needs no ivars, no pinning and no reset. It has no `new`: the object is
the process's, handed out by `Resource#request` and made by nobody
else. Null outside a run frame, and every accessor checks — reaching
the request object from anywhere else is a mistake worth naming, not a
segfault.

The accessors keep webmachine-ruby's meanings: `uri` is the
request-target as it arrived, query and all; `disp_path` is what is
left of the path for the resource to dispatch on (the splat tail where
the route has one, the whole path where it does not); `path_info` maps
the Symbol tokens the route bound, by name; `path_tokens` is the
splat's segments in order, an empty Array where there is no splat.

Query decoding: `+` is a space (HTML form encoding, which is what a
query string is in practice), and a truncated or non-hex escape is kept
**verbatim** rather than guessed at — a decoder that invents bytes is
worse than one that hands them back. `key=value` pairs are `&` or `;`
separated; a repeated key keeps the **last** value, which is what a
Hash means; a key without `=` maps to `""`.

`request.headers` on a **parked h2 request** does not refuse "never" —
it refuses **gone**. That request answers after its decode buffer is
gone, so there is nothing to lend and nothing will be invented.

A websocket resource and an SSE resource are not `Resource`s, but both
still read the head that asked, through the same one object — which is
why that accessor is hung on all three classes.

<a id="mruby-refusals"></a>
### What a resource may not do yet, and says so by name

Callbacks whose **values** the machine cannot speak yet refuse the
start rather than silently doing nothing: the `*_provided` pair arrays
beyond content type, `is_authorized?` returning anything but an
unconditional true (a 401 with `WWW-Authenticate` needs the callback's
string), `moved_*` (a truthy answer carries a Location URI), and
`generate_etag` — which stays refused until real per-representation
ETag support lands, so the gzip work cannot promise a distinct ETag per
coding.

Method lists (`known_methods`, `allowed_methods`) cross the boundary as
**one String** like `'GET HEAD POST'`, tokenized from its bytes — no
Ruby arrays cross. A token outside the compiled set is refused, because
a method the walker cannot name would silently 501.

`encodings_provided` is webmachine-ruby's Hash of coding name → encoder
method, and **only the keys are read**. The values name a
per-representation encoder callback that no tier honors yet — gzip is
built in, by zlib, at answer time — and that is documented at the one
place the declaration is read.

<a id="app"></a>
## The application surface

`Webmachine::Application.new { |app| ... }` is the app's whole surface,
and it is C. The block configures a listener, adds routes and leaves a
`ready` hook, and by the time it returns everything a request will ever
need is a table.

The app file defines **one** method, `main`. `app_load` calls it. There
is no inheritance hook, no ivar, no `mrb->ud`, and no constant scan —
`route.add` is the only door, and it is the door that freezes the
class. `main` is asked for straight in the method table: no
`respond_to?`, and no funcall that would report a missing `main` as a
NoMethodError instead of as the refusal it is.

`--app` takes precompiled `.mrb`; this server never compiles Ruby
itself. A `.rb` is refused **by name**, with the `mrbc` line that
produces what `--app` wants — compiling it as a fallback is how the
source path would come back in through the side door.

<a id="app-registry"></a>
### The registry

Every AppSpec ever built lives in a file-static registry; `registered_`
names the ones whose block **returned**. `Application.new` without a
block builds a spec nobody serves — legal, and deliberately inert.

A file-static rather than `mrb->ud` or a Ruby constant: the server is
one process, one VM, one ring, and the tool reads it straight after
`main` returns. Nothing on a request path touches it. The same
reasoning makes the request view a file-static.

Registration order **is** listener order, and a connection's listener
index is how the writer finds its app again.

<a id="app-listener"></a>
### Exactly one listener spelling per app

`conf.port` / `conf.unix_path` / `conf.url` — a second one refuses by
name. Several **apps** may each name their own; several listeners for
one app is what nothing has asked for, so nothing builds it.

Two applications may not name the same listener, and they are compared
on the **listener**, not on the spelling: `conf.port = 80` and
`conf.url = "http://host:80"` are two ways to say one socket, and a
refusal that only looked at the spelling would miss that pair. Two
port-0 asks are **not** one socket — the kernel picks a fresh ephemeral
port for each bind, so they collide with nothing.

`conf.url` reads both ways: before the bind it spells where this app
**wants** to be, after it where it really is. `:0` is legal in a url,
same contract as `conf.port = 0`; an **empty** port (`http://h:`) is
not a zero, it is a malformed url.

<a id="app-facades"></a>
### The facades are built once

The conf and routes objects are views of one AppSpec, and a view has no
reason to be manufactured per access. They are built once in
`Application.new` and hung on the object as ivars — rooted by the
object that owns them, so no `mrb_gc_register` and no second lifetime
to reason about — and `app.conf` is the same object every time, which
is what a reader should mean. `attr_reader :conf` in
`mrblib/webmachine.rb` is the whole accessor.

Neither class carries a constant, so an app file can neither reopen nor
instantiate them; they are rooted by hand at init, because a class
nothing names is collectable.

The **canonical** surface is direct writes: `app.conf.url = "..."`,
`app.conf.port = 8080`. The block forms — `configure` / `config` /
`routes` — exist for webmachine-ruby compatibility only: tests pin
them, the examples never show them. `configure` and `config` are the
same method under two spellings, not two methods. A block stays
canonical exactly where it **is** a callback: `app.ready`.

<a id="app-removed"></a>
### What was removed, and why

- **`conf.adapter=`** accepted a value and threw it away, so a file
  naming a reactor this tree does not have "worked" while doing
  nothing — the silent fallback this tree forbids everywhere else. Its
  compatibility promise ("a webmachine-ruby file runs unchanged") was
  worth less than the lie, so that promise is **withdrawn**: a file
  naming an adapter now gets NoMethodError, which is true.
- **`conf.ssl=` / `ssl_options=` / `certificate=` / `certificate_key=`**
  reserved names for a TLS that is not in this tree — code on stock
  with no second user. When TLS returns it brings its own setters;
  until then NoMethodError says exactly what is the case.
- **`route.sse`** was proposed for deletion as a reserved name and then
  **kept**, because SSE landed: it is a signpost to a feature that
  exists, which is content and not a lie. `route.assets` is the same
  case and was never in doubt.

<a id="app-errors"></a>
### Named refusal classes

Until recently every refusal raised `RuntimeError` — the anonymous
catch-all — which made a server's refusal indistinguishable from any
RuntimeError an app raises itself, and left `rescue` no way to mean
"webmachine said no".

**Three** classes, because this tree makes exactly three distinctions:
a configuration that cannot stand (`ConfigError`), a route that cannot
be built (`RouteError`), and everything else (`Error`). More classes
than distinctions would be decoration.

What is genuinely **Ruby semantics** keeps its Ruby class: a `TypeError`
for a wrong return type, a `KeyError` for a missing key — a refusal by
the server is a different thing from a mistake in a value.

Macros rather than helpers, in the shape the neighbouring gems use
(mruby-toml's `E_TOML_ERROR`): the lookup is a presym pair and happens
only where something is already going wrong.

<a id="app-routes"></a>
### The routes

**The token array crosses the boundary once**, for all three route
kinds. From that point a route is bytes and offsets in a flat table,
and no Ruby object is looked at again on any request path. The refusal
messages name the method — `route.add` and `route.sse` are different
mistakes to make.

A String token is a literal segment, a Symbol binds one, `:*` is the
tail. The Symbol's own id rides into the table, because the request
object names what a span captured and this is the only moment the name
exists.

**Three tables, not one.** Websocket routes share nothing with the
flow — no status, no negotiation, no method test — and an SSE path is
matched before the graph or not at all, because there is nothing there
to decide. A second and third table cost one pointer compare on the
paths that use them and keep the flow's table exactly as wide as the
flow.

Both protocols walk the **same** table of the same app in the same
registration order, so a route cannot mean two things depending on
which wire carried it. The **first** route that matches wins.

A miss is 404 from the prebuilt store, **before B13** — therefore
before any method test, so POST on an unknown path is 404 and never
405.

<a id="app-spans"></a>
### What a match captures, and why it captures it at all

Nothing reads the spans yet on most paths. They exist because the
**capture is where the cost would be**: the match loop has the segment
boundaries in registers exactly once, while it is walking. The lazy
request object turns them into Ruby values on demand, and a resource
that never asks pays for two pointer stores the loop was going to
compute anyway. Adding the capture later would mean walking the path a
second time, which is the one shape this router exists to avoid.

`RouteSpans` has **no member initializers**, deliberately: it is
scratch the match loop fills in, and a declaration at the top of a
request path would otherwise zero 16 spans — 256 bytes of stores per
request that nothing reads. A miss leaves all of it indeterminate, and
the caller has nothing to read on a miss anyway.

A route under construction is rolled back **whole** by `abandon()`, so
a route that fails validation leaves nothing half-registered. Past the
binding limit a route refuses at `add_route` by name, so the match loop
never has to test.

Without a splat every segment must have been spoken for — `/fizz/buzz`
is not `['fizz']`. With one, `:*` is the last token by construction, so
the rest of the path **is** the tail — including the empty tail, which
is why `/fizz` matches `['fizz', :*]` as well as `/fizz/a/b` does.

<a id="app-bundles"></a>
### One writer, N apps

Every app's routes go into **one** bundle vector, back to back; the
app's slot remembers where its own start. A request indexes once (base
+ the router's verdict), and the date patch stays one loop for the
whole process however many apps it serves.

The **status supply** stays one per app: a 400 is the same bytes
whoever was going to answer. Everything that carries a **resource's**
own voice — its 200 in every shape, its Allow, its negotiated type, its
gzip decision, its h2 blocks — lives per route, and the router's
verdict is the only thing that chooses between them.

Each route's index table starts as a copy of the generic one and then
points 200 and 405 at that route's own entries, appended to the same
shared store. That is why a matched request still indexes **once**,
with no status compare and no second table: the multi-resource cut
costs setup memory, not a single per-request branch. The slots are
`uint16_t` — two per route would otherwise cap an app at ~113 routes.

The generic table's own 200 and 405 are built **neutrally** (no content
type, no Allow) so the index stays total for any status the flow tables
can name. A matched route never reads those two; a miss only ever reads
404.

<a id="log"></a>
## Logging, and the law

<a id="log-two-processes"></a>
### Why it is two processes

Formatting a combined-log line in-process measured **71.5 ns each** —
date and number spelling plus an escape scan over every request byte.
Filling a fixed header and memcpying the raw strings measures **17 ns**.
So the server ships **records** over a unix socketpair to
`webmachine-logd`, which formats, escapes and batches to disk on its
own core, where its 70 ns cost nobody. Batched `write(2)` moves 3.8M
lines/s in the slowest container this tree benches on.

The daemon is deliberately dumb: blocking reads, one `write(2)` per
filled batch, no ring, no threads. Its budget is enormous next to its
load.

<a id="log-rule"></a>
### The one rule

**Every line we decide to write must land on disk.** No drop path
exists on either side: the server's buffer grows until the kernel took
the records (the write SQE rides the submit that was happening anyway,
a short write resumes, a dead daemon is a named refusal), and the
daemon's only job is to drain, format and write. A write error is a
named refusal with a nonzero exit, never a silent hole.

`send`, not `write`: the log fd is the daemon's socketpair, and a dead
daemon must come back as `-EPIPE` in the CQE, not as a `SIGPIPE` that
kills silently.

<a id="log-two-streams"></a>
### Two streams, two sockets, two code paths

An access line and an error line share **no field — not one** — so
nothing is shared but what is 1:1 identical, which is the transport.
Each stream has its own socketpair, its own daemon, its own file and
its own record struct with its own version byte. Reusing one record for
both would have meant fields that lie about what they hold.

Same machine, same build, so the **struct is the format**: no
endianness ceremony, one version byte per stream so a mismatch refuses
instead of misparsing.

- **Access** batches: its records are small and constant-shaped, so the
  whole batch goes in one send and the daemon walks them itself.
- **Error** ships **one record as two linked sends**: a fixed header
  whose last field is the size of the dynamic half, then exactly that
  many bytes. The daemon reads `sizeof(ErrRec)`, learns the number, and
  reads exactly that — no scanning, no partial-record guessing, and a
  bound the reader knows before it allocates. Errors are rare, so one
  record per round costs nothing worth batching for.

**`MSG_WAITALL` is what makes the link safe.** `IOSQE_IO_LINK` only
breaks a chain on **failure**, and a short send is not a failure — so
without it a header that went out half would be followed by a body sent
from the right offset regardless, and the daemon's framing would desync
permanently, one record after the next. With `MSG_WAITALL` each half is
all-or-error. `-ECANCELED` on the body is the linked op after a header
that failed: one refusal, not two.

The daemon cross-checks anyway: `dyn` is what the second send carried
and the five lengths are what it is made of. The server computes both
from the same numbers, so a disagreement is a **desynced stream**, not
a bad record — every following byte would be misread — and it refuses
by name.

<a id="log-error"></a>
### What is an error, and what is not

One thing that went wrong **inside the app**: a callback that raised.
Not a refusal the server decided — those are named on stderr at startup
and are the operator's own doing — and not a status: **a 404 is an
answer, not an error.**

The error log is written **before** the exception is consumed for the
peer's body: the peer only ever learns "500", the operator learns which
class raised what, and where. The log never decides when an error stops
existing — every caller clears `mrb->exc` itself the moment it is done.

An error entry is a header line plus one indented line per backtrace
frame, because a trace read sideways is a trace nobody reads. Frames
are escaped like every other request-touched field, so a raise carrying
`\n` in its message cannot forge one. An empty trace is a build that
kept nothing, not a lost one.

**What a trace contains is decided by the `.mrb`, not by the binary,**
and it was measured rather than assumed: `mrbc -g app.rb` puts the
locations in the bytecode, and then **both** the ship build and the
debug build spell real frames (`app.rb:3:in to_html`); plain `mrbc`
leaves one `(unknown):0` that no build can recover. The server's own
`conf.enable_debug` governs frames from mruby's **core**, not from the
app.

<a id="log-escaping"></a>
### Escaping happens in the daemon

Quotes, backslashes and control bytes in request-controlled fields are
escaped there — an attacker's header must not forge log columns, and
the serving core no longer pays the scan.

<a id="log-privacy"></a>
### Privacy is a level of privacy, not a level of address

| level | what a host spells |
|---|---|
| `none` | no privacy — the address as-is |
| `anon` | IPv4 with the last octet zeroed, IPv6 cut to its /48 (default) |
| `full` | full privacy — every host spells `-` |

**The server never sees a spelled address.** The raw sockaddr bytes
exist only in transit and, at anon and full, never reach the disk at
all.

A full IP is personal data under the GDPR (art. 4(1); ECJ C-582/14 said
so even for dynamic IPs), so `--log-privacy none` prints a warning at
startup: that is a legal choice, not a technical one, and the server
says out loud what the operator just took on. Precisely: no cookie
banner is forced by a server log — that duty is ePrivacy, about the
client's **device**. What full addresses need is an art. 6 basis and
disclosure; security logging with short retention usually rides
legitimate interest plus a privacy notice, while using the addresses
beyond that needs consent. Default `anon`, which the authorities treat
as no longer personal.

`DNT: 1` and `Sec-GPC: 1` are respected: the daemon caps that record's
`%h` at anon even when the operator chose `none`. It can only ever
**add** privacy, never remove it. Neither is a flow fact — `plain` is
untouched, the graph decides nothing by them. `1` is the only defined
opt-out value; `0` is explicit consent and stays false.

The **error** stream carries no privacy switch and spells a peer at
anon, always. A trace is a debugging aid and debugging never needed the
last octet; an operator who wants full addresses asks on the access
log, where the warning is attached to the asking.

<a id="log-cap"></a>
### The size ceiling

`--log-max-bytes` is a **hard ceiling on the file, not a rotation**: at
the cap the oldest entries are dropped and the newest kept, **in
place**. A server under load can write faster than anyone reads, and a
log that only grows fills the disk and takes the machine with it.
Rotation would only move the ceiling to twice the number and keep
growing.

**500 MB by default**, not "no ceiling": a server that logs and was
never told a number would otherwise write until the disk is full, and
taking the machine down is a worse failure than losing the oldest
requests. `0` is still legal and means no ceiling — the operator saying
they watch it themselves.

One switch for **both** files, because it answers one question ("how
much disk may logging cost me?") and two numbers would only ask the
operator to do the addition themselves.

This does not weaken the one rule: every line the server decided to
write still lands on disk. What the cap governs is how long it
**stays** there, which is retention and the operator's choice.

The cut is moved forward to the start of the next whole **entry**, not
just the next line: a file that opens with three orphaned backtrace
frames of an entry that is gone reads like a bug. Continuation lines
are the ones starting with a tab, and no access line ever does — so
that rule is a no-op on the access stream rather than a second rule for
it.

Amortised cost: keeping half the cap means the copy runs once per
`max_bytes/2` written and moves `max_bytes/2`, so **one extra byte
moved per byte logged** — the price of a bounded file, paid on the
daemon's core and not the server's.

The log file is opened `O_RDWR` and deliberately **not** `O_APPEND`:
on Linux `O_APPEND` drags `pwrite(2)` to the end of the file whatever
offset it is given, and the cap writes to offset 0. One process writes
this file, so the seek position is ours alone and append semantics buy
nothing. The daemon seeks to the end at start, so a restart into an
existing log inherits its size instead of pretending it starts at zero.

<a id="log-h2"></a>
### What the h2 log cannot say

Referer and user-agent are `-` by **honesty**: an h2 answer can run
after its decode buffer died, and the two fields were never worth
copying per stream for a log column. The method column spells itself
from the enum; `kOther` logs `-`, because the name was never kept and
inventing one would be a lie in a log.

`%b` is what the answer **says**, not what the round sent — the full
body length even when the peer's window parks a remainder. For a
dynamic 200 it is the identity length: the gzip arm's wire size is
conneg's secret, and re-deciding it for a log column would be work per
line. Prebuilt-store answers log `-`, their body lengths having been
baked in at build.

A wire-invalidity refusal has no request to describe, so every request
field spells `-` and the status is the story.

<a id="cfg"></a>
## The config file

`webmachine.toml` says what the command line says — listener override,
app bytecode, asset archive, logs, pidfile, ring tunables — in the
format every deployment tool already reads and writes.

**Precedence, one line: CLI > file > the app's `conf`.** The file is
the invocation's second voice, so the typed flags beat it and both beat
what `main` configures.

**What the file cannot do: create resources.** No routes, no bodies, no
apps — Ruby owns behavior, the file owns operation. A server with no
app file still serves, because the default splat resource and the asset
archive are apps the *tree* provides, not ones the file created.

The parser is mruby-toml, through the VM the process already carries:
config is read once at startup, never on a request path, so the
Ruby-side surface is exactly enough and the binary carries no second
TOML implementation. The VM is therefore booted **before** the config
is read.

Every refusal is by name. A TOML error carries the parser's own words —
they name the line and the reason better than a paraphrase would. A
wrong type or value says what it is and what it takes. The privacy word
is checked **there**, where the operator can still read the answer, and
not in the daemon after the fork.

`Document#[]` raises `KeyError` for an absent section, which here just
means "the CLI or the app's conf speaks"; any other raise is the file's
problem. Everything worth keeping is copied into `std::string`s before
the arena closes.

Without `--config`, `./webmachine.toml` is used when present — **and
announced**, so an invisible file never silently steers a server. An
explicit `--config` that cannot be read is a refusal.

Bounds that are checked because the kernel would otherwise refuse
later: `sq_entries` ≤ 32768 (`IORING_MAX_ENTRIES` — more is not "more
headroom", it is `-EINVAL` at init), port 1..65535, and
`log.max_bytes` ≥ 4096 (a cap smaller than a line keeps nothing, and
half of it — what the daemon keeps — has to hold at least one whole
entry to be a log).

The **invocation speaks first, and once**: nothing in `ServerOptions`
is reachable from Ruby, deliberately. An app file that could rewrite
the command line would make the command line a suggestion.

The pidfile is written **before** anything can fail, so a file that
exists names a process that at least got that far, and removed on the
way out. The alternative is worse than it looks: `pkill -f
webmachine-server` also matches the shell that typed the command, which
is how an afternoon gets spent.

<a id="floor"></a>
## The floor binary

`webmachine-floor-epoll` is the measuring stick, not a product: the
same floor protocol as the ring server — one fixed 200 per receive,
`--echo` for the byte proof, TERM removes the unix path — built on the
classic reactor (epoll, accept4, recv/send, edge-triggered,
read-until-EAGAIN). **The distance between its number and the ring
floor's number is what io_uring buys on this hardware**; nothing else
separates the two binaries. Its signalfd sits inside the epoll set, so
its stop is an event like every other — the same race-free lifecycle.

The edge-triggered contract is read-until-EAGAIN or the edge is lost.

<a id="hints"></a>
## Prediction hints

Only where the taken side is **terminal** — an exit, a raise, a
connection's death, an invariant violation. A branch that swings
naturally at runtime carries **no** hint: a static hint on a swinging
branch is a systematic mispredict. "A resource either declared gzip or
it never did" is deployment-stable, not swinging, and gets none either
— it is decided at setup.

<a id="cpp"></a>
## The C++ this tree allows

The 9110 layer is header-only, mruby-free, and everything in it is
`inline` or `constexpr`, so it inlines into its caller and the machine
code is identical to the copy it replaced. Sharing costs nothing, which
is the only reason it happens.

Where a driver needs version-specific hooks it takes them as a
**template parameter** and monomorphises — the `Ring<App>` shape.
`header_switch` does the same with a functor: one length-switch stays
one dispatch per header, the 9110 cases are filled in place, and every
name this layer does not own falls through to the framer's functor,
which inlines at each call site where the case's length is a known
constant. The compiled result is exactly the one fused switch the loop
always was.

**Forbidden:** `virtual`, `std::function`, `variant` + `visit` — each
is indirection or allocation per request.

Functions that are one or two lines and only rename a single call do
not exist; their code lives at the call site. Header-inline value
helpers with many callers are not that (in the binary there is no
function), and neither is a `unique_ptr` deleter for an incomplete type
across a translation-unit boundary — that is a job, not a rename.

`rd16`/`rd32`-style byte readers are not written here: miniz's own
`MZ_READ_LE16`/`MZ_READ_LE32` are already compiled in and are better
(they pick the unaligned fast path per platform).

<a id="graves"></a>
## Open questions attached to graves

- **The bitset walk on a shared vCPU.** It led in the container (60 vs
  70 ns) and lost on both real machines. If a cloud instance ever
  becomes a measured target, resurrect and re-measure **there** — never
  on this evidence alone.
- **h2spec 3.5/2.** Failed by name, for a stated reason. It becomes a
  real question only if this listener ever stops speaking HTTP/1.1.
- **Autobahn's blind spot.** The conformance fixture cannot reach the
  application-initiated close, so that path needs a fixture that
  returns a Symbol, and a client that answers a server-initiated close.
- **A peer that only sends** dies at the header clock. Revisit when
  bodies get a consumer and pings are answered on the timeout path.
